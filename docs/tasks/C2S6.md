## 2) Diseño del registro

### 2.1 Nombre y ubicación

- **Nombre:** `OperatorRegistry` (alias de construcción: `OperatorRegistry::default()` con los 10
  operadores built-in precargados; nombre validado contra alternativas: `BackendRegistry` (S2)
  es de backends, no de operadores; `OperatorTable` sugiere tabla estática; `ExtensionPoint`
  es genérico. `OperatorRegistry` es el término estándar Volcano/CBO y no colisiona).
- **Dónde vive:** nueva hoja neutral **`src/operator_registry.rs`** (1 fichero, cero deps
  intra-crate salvo `query::{LogicalOperator, PhysicalOperator}`, `storage::StorageEngine`,
  `error::Result` — mismo nivel que `search_profile.rs`, NO dentro de `planner.rs` ni
  `physical_plan/mod.rs` para no crear ciclo `planner ↔ physical_plan`).
  - `lib.rs`: `pub mod operator_registry;` (orden alfabético, junto a `search_profile`).
  - Ciclo prohibido: `operator_registry` NO importa `planner` ni `executor` ni `governor`;
    `planner`/`cost_estimator`/`query` importan desde `operator_registry` (dirección downward,
    verificable con `cargo modules dependencies --lib --acyclic`).

### 2.2 Contrato tipado (Contract First — la spec, el impl sigue)

```rust
// src/operator_registry.rs — CONTRATO (firmas + semántica + errores)

/// Cómo compila UN operador lógico a su fragmento físico.
/// Recibe el operador + el storage; devuelve un `PhysicalOperator` Volcano
/// ya construido (el planner lo encadena al `current_operator` como hoy).
/// Error: `VantaError::Schema` si el operador está mal formado (ej: Join sin spec),
/// `VantaError::Storage*` si la construcción necesita leer storage y falla.
/// Idempotencia: construir dos veces el mismo op da dos operadores equivalentes.
pub trait OperatorCompiler: Send + Sync {
    fn operator_name(&self) -> &'static str; // "scan" | "dedup" | ...
    fn compile_logical(
        &self,
        op: &LogicalOperator,
        storage: &StorageEngine,
        ctx: &CompileContext<'_>, // sub-planos ya compilados + selects de CBO
    ) -> Result<Box<dyn PhysicalOperator>>;
}

/// Cómo costea UN operador lógico dado el `in_rows` entrante.
/// Semántica idéntica a `estimate_operator` actual: rows top-down, bytes = rows*AVG.
pub trait OperatorCostModel: Send + Sync {
    fn operator_name(&self) -> &'static str;
    fn estimate(&self, op: &LogicalOperator, in_rows: f64, ctx: &CostContext<'_>) -> OperatorCost;
}

/// Registro. Clave = `&'static str` (nombre del operador, NO el enum variant).
/// `compile`/`estimate` hacen dispatch por nombre; operador desconocido → `Err(Schema)`
/// en compilación y passthrough `in_rows` en costo (nunca panic).
pub struct OperatorRegistry { /* BTreeMap<&'static str, Entry> + built-ins precargados */ }

impl OperatorRegistry {
    pub fn new() -> Self;                    // solo built-ins (10 operadores §1)
    pub fn register<C, M>(&mut self, name: &'static str, compiler: C, cost: M) -> Result<()>
    where C: OperatorCompiler + 'static, M: OperatorCostModel + 'static;
    // Error: `Schema("duplicate operator '...'")` si el nombre existe (aditivo, no override silencioso).
    pub fn compile_logical(&self, op: &LogicalOperator, storage: &StorageEngine, ctx: &CompileContext<'_>) -> Result<Box<dyn PhysicalOperator>>;
    pub fn estimate(&self, op: &LogicalOperator, in_rows: f64, ctx: &CostContext<'_>) -> OperatorCost;
}
```

- **Clave por nombre, no por variante:** el enum `LogicalOperator` sigue existiendo (compat),
  pero el dispatch NO es `match op` sino `registry.compile(op.name(), ...)`. Un operador nuevo =
  nueva variante enum + `register("nombre", ...)` en composición, **cero `match` editados**.
- **`CompileContext` / `CostContext`:** structs `#[non_exhaustive]` con lo que hoy es captura
  implícita del planner (`storage`, `sorted_filters` ya ordenados, `joint_selectivity`,
  `has_join/join_spec`, `search_profile`) + `registry: &OperatorRegistry` para recursión
  (Join/SubqueryFilter compilan sub-planos vía `ctx.compile(&sub_plan)`). Evita que cada
  compiler reimplemente CBO.
- **Errores:** un solo `VantaError` con `code` estable (`SCHEMA_UNKNOWN_OPERATOR`,
  `SCHEMA_DUPLICATE_OPERATOR`); sin `panic`/`unwrap` en hot path; `open/next/close` ya
  retornan `Result` (Volcano existente, sin cambio).
- **Hyrum surface (qué se garantiza / qué NO):**
  - Garantizado: orden de encadenado físico (scan→filtros→vector→sort→project→limit, join con
    filtros post-join), `Send+Sync` en todo lo registrado, costo `estimated_bytes ≥ 0`.
  - Explícitamente NO garantizado: orden de iteración de `list`/scan (documentar *unordered*),
    texto de mensajes de error (solo `code` es contrato), byte-layout en disco.

### 2.3 Cómo se registra un operador nuevo SIN editar planner/executor probados

```
worker slice 1: crea src/operator_registry.rs con el contrato + registry + built-ins
                (los 10 arms actuales se MUEVEN como `register("scan", ScanCompiler, ScanCost)`…;
                 planner.rs:109-163 se reduce a `for op in &plan.operators { registry.compile(...) }`
                 + la cadena física :205-305 se reduce a helpers llamados desde cada compiler).
worker slice 2: `Query::into_logical_plan` / `SelectStatement::into_logical_plan` emiten la
                nueva variante (solo query.rs productor + nuevo fich. físico). planner.rs,
                executor.rs, cost_estimator.rs, governor.rs NO se tocan.
worker slice 3: test de extensión (ver §3) registra el operador ejemplo contra un
                `OperatorRegistry::new()` local y compila un plan que lo contiene.
```

- **planner probado:** tras slice 1, `optimize_and_compile` es un loop sobre el registry
  (orquestación estable, cubierta por tests existentes sin modificar). Añadir operador =
  añadir entrada al registry en el `new()` / composición, no editar el loop.
- **executor probado:** `execute_plan:463` y `execute_statement:178` NO cambian (H3: executor no
  matchea `LogicalOperator`). El operador nuevo fluye por el mismo driver Volcano.
- **cost_estimator:** `estimate_operator:201` se reduce a `registry.estimate(op, in_rows, ctx)`;
  cada operador lleva su `OperatorCostModel`. Operador sin modelo registrado → passthrough
  `in_rows` (igual que hoy `Sort/Project/Join/SubqueryFilter`, documentado, no panic).
- **physical_plan:** cada físico sigue en su fichero (`filter.rs`, `sort.rs`, …); el operador
  nuevo añade SU fichero (`dedup.rs`) + 1 línea `pub use` en `mod.rs` + su `register(...)`.
  Los 7 fich. existentes NO se editan (salvo `mod.rs` re-export, aditivo).
- **One-Version Rule:** un solo `OperatorRegistry`, una sola versión viva de
  `OperatorCompiler/OperatorCostModel`; extender con métodos con default o structs
  `#[non_exhaustive]`, jamás `OperatorRegistryV2`.
- **Naming (tabla §3a del arch):** trait `OperatorCompiler`/`OperatorCostModel` (verbo+sustantivo),
  métodos `compile_logical`/`estimate` (snake_case verbo), config `operator_name` (snake_case),
  feature-gates kebab-case si alguno (ninguno previsto; `embed-local`/`remote-inference`
  se propagan vía `CompileContext`, no vía features del registry).

## 3) Operador-ejemplo propuesto + test de extensión

### 3.1 Operador-ejemplo: `Dedup { field: String }` (el más barato que prueba la extensión)

**Por qué `Dedup` y no otro:** es unario (1 hijo, sin sub-planos ni storage), puro en memoria
(HashSet de `FieldValue` vistos), sin embeddings ni features (`remote-inference`/`embed-local`
irrelevantes), reutiliza `PhysicalFilter`-style (envoltorio Volcano sobre `child`), costo trivial
(passthrough con factor 1.0 o heurístico `*0.9`), y no existe hoy (garantiza que el test prueba
registro real, no un built-in). Alternativas descartadas: `Traverse` físico (requiere grafo BFS,
caro), `Aggregate` (requiere semántica group-by, diseño mayor), `Distinct` global sin campo
(requiere hash de nodo entero, más caro que por campo).

- **Lógico:** `LogicalOperator::Dedup { field: String }` (emisor futuro: `SELECT DISTINCT field`
  o `DEDUP BY field`; en S6 el productor puede ser solo test-construido — H2 autoriza
  operador "solo-físico" sin parser).
- **Físico:** `PhysicalDedup { child, field, seen: HashSet<String> }` en nuevo
  `src/physical_plan/dedup.rs` (`open` limpia `seen` + `child.open()`; `next` salta nodos cuyo
  `relational[field]` ya visto — serializado a string para hashear; `close` delega + limpia).
- **Costo:** `in_rows * 0.9` heurístico documentado (o passthrough 1.0 si se prefiere cero
  invención; decidir en slice 2, documentar en docstring del `DedupCost`).
- **Compilación:** `DedupCompiler::compile_logical` envuelve el `current_operator` (igual que
  `Sort/Project/Limit` hoy en `:283-303`): `Box::new(PhysicalDedup::new(child, field))`.
