# VantaDB — HNSW & Lexical Engine Performance Benchmarks

This document compiles the certified performance metrics for **VantaDB** at the MVP version. It covers both the internal Rust engine tests (**Stress Protocol**) and telemetry from the Python SDK wrapper.

---

## 📊 1. Core Engine Certification Results (Rust)

These results come from the **Stress Protocol** (`tests/certification/stress_protocol.rs`), a 7-block certification suite that validates Recall consistency, scalability, HNSW memory consumption, crash persistence, and graph consistency.

> [!NOTE]
> These metrics are run under the heavy certification suite (`.github/workflows/certification.yml`, job `stress-protocol`) on GitHub-hosted `ubuntu-latest` CI runners with AVX2 vector instruction support. GitHub rotates the underlying runner hardware — treat these values as run-scoped certification output, not a fixed-machine baseline.

**Reproduce (Regla 11):** `cargo test --release --test stress_protocol -- --nocapture --test-threads=1` — same invocation as the `stress-protocol` job in `.github/workflows/certification.yml`.

## ⚠️ Limitations and Technical Considerations

1. **Synthetic Data:** Current tests run on random L2-normalized vectors (uniform distribution). Real-world index behavior may vary slightly with actual production datasets (e.g., real text/embeddings for RAG).
2. **Single-threaded Construction:** The ingestion and HNSW graph construction phase is currently single-threaded in the SDK API.
3. **Distance Metrics:** The current version is highly optimized for **Cosine Distance**.

## 🚀 5. Impact of Loop and HNSW Distance Optimization (Phase 2)

## 📦 10. Node.js Bindings: vantadb-node (napi) vs vantadb-ts (WASM) — PERF-BENCH-01

> **Source of truth:** `vantadb-node/bench/bench-abi.mjs` (extended 2026-08-30 with per-op p50/p95/p99 percentiles).
>
> **Reproduce (Regla 11 — medición antes de decidir):**
>
> ```bash
> # canónico (pre-mortem Fallo 2: dataset determinístico seed 42)
> # Reducido aquí a 10k × 1536d × 100q por budget wall en este sandbox (bun);
> # la shape completa (100k × 1536d × 1k) es válida con Node ≥22 + release build (~5-10 min).

>
> **Fairness caveat (by design, not a bug):** `vantadb-node` (napi) usa persistent fjall storage on disk → paga fsync; `vantadb-ts` (WASM) en Node usa engine in-memory (Node no tiene OPFS). Comparar la rama WASM en el browser (con OPFS/IDB) es justo; en Node, el native siempre será más lento en insert por fsync.
>
> **Limitación del sandbox (2026-08-30):** este ambiente corre bajo **bun 1.3.14** (Node 22+ no instalado). Bun no soporta ESM `import ... from "*.wasm"` desde paquetes npm sin plugin, por lo que la rama WASM falla en init (`wasm.vantadb_new undefined`). La rama nativa sí corrió completa. El comando canónico para la rama WASM es **Node ≥22**, donde `vantadb-ts` corre sus tests OK via vitest con `server.deps.external: [/vantadb-wasm/]` (ESM wasm nativo de Node 22+).

**Lectura:**

### Comparación tamaño binario (ambos prebuilt, 2026-08-30)

| Backend | Artefacto | Tamaño |
| :--- | :--- | ---: |
| **`vantadb-node` napi** | `vantadb-node/vantadb_native.win32-x64-msvc.node` | **4.51 MB** |
| **`vantadb-ts` WASM** | `vantadb-wasm/pkg/vantadb_wasm_bg.wasm` | **1.35 MB** |

Lectura: el `.node` nativo es ~3.3× más grande que el `.wasm` (4.5 MB vs 1.35 MB), pero el WASM paga el costo de cold-start (`init()` async + compilación streaming del módulo ~50-150 ms en Node 22+, hasta ~500 ms en browser). El native está precompilado y carga instantáneo.

### Posicionamiento (decisión tomada: native primario en Node, condicionada a números)

**Decisión:** en runtimes Node.js, **`vantadb-node` (napi native)** es el backend primario. Razones medidas:

1. **No hay cold-start WASM** en `.node` (precompilado). En serverless/edge functions el cold-start WASM es prohibitivo.
2. **Persistent storage real** (fjall + WAL) en Node, mientras WASM en Node es in-memory puro (no OPFS disponible).
3. El `.node` (4.5 MB) es justificable en server-side; el `.wasm` (1.35 MB) gana en bundle size del lado browser.

**Limitaciones declaradas (Regla 11 — claim sin fuente reproducible no existe):**

- Los números de **insert** están dominados por fsync — en benchmarks no-persistentes (WASM browser con OPFS) la comparativa justa requiere medir allá, no acá.
- Los números de **search_hybrid** son sensibles a la implementación del materializador de snippets (cambia entre versiones); no usar para claims de posicionamiento, sí para detectar regresiones.
- **WASM side no se midió en este run** (limitación de sandbox — ver arriba). Decisión posicional se mantiene **condicionada** al run completo en Node ≥22.

## 13. Ingestión multi-consumidor — `Arc<Mutex<mpsc::Receiver>>` A/B (RES-03)

> **Source of truth:** `benches/ingestion_concurrent.rs` (nuevo, `required-features = ["async-ingestion"]`).
> Pregunta de la tarea: ¿el receiver compartido bajo mutex en `src/ingestion.rs:72`
> (patrón multi-consumidor de un canal mpsc single-consumer) es el cuello de botella
> de throughput de la ingesta, y conviene un canal multi-consumidor nativo
> (`crossbeam-channel` / `flume`)? Regla 9: medir antes de rediseñar.
>
> **Reproduce (Regla 11):**
>
> ```powershell
> cargo bench -p vantadb --bench ingestion_concurrent --features async-ingestion
> ```
>
> **Nightly coverage (FIND-70):** `heavy-bench-nightly-51.yml` (`light-benchmarks`)

> (`required-features` in `Cargo.toml`, otherwise cargo silently SKIPS the bench).

### Premisas verificadas en discovery (2026-09-03)

- `tokio::sync::mpsc` es **multi-producer, SINGLE-consumer** por diseño (docs oficiales:
  <https://docs.rs/tokio/latest/tokio/sync/mpsc/>). La opción "migrar a tokio::mpsc nativo
  multi-consumidor" NO existe: `Receiver` no es `Clone` y `Arc<Mutex<Receiver>>` es precisamente
  el patrón recomendado para compartirlo entre tasks. El código actual ya lo usa.
- Los consumers son tasks async (`tokio::spawn` + `recv().await`) y el insert del motor va en
  `spawn_blocking` fuera del guard (regla `concurrency-async.md` R1/R2). La sección crítica del
  mutex es solo el `recv()` (dequeue), no la inserción.
- `crossbeam-channel` (Receiver `Clone`) es sync — con consumers async obligaría a `spawn_blocking`
  por recv o bloquear el event loop → más complejidad, no menos.
- `vantadb-wasm` compila el core con `default-features = false, features=["wasm"]` →
  `ingestion` (feature `async-ingestion`) **no entra al build wasm** (cero riesgo de dep wasm).

#### Verificación ERR-010 del path `commit_transaction` (`txn.rs:119-213`) — VIOLA

`commit_transaction` hace WAL `batch_append([Begin+ops+Prepare])` (L159-161) y

está en el snapshot = **invisible record en recovery** (replay los salta por
`≤ checkpoint_seq`). **Veredicto: VIOLA ERR-010** (ventana pequeña — requiere
`flush()` concurrente durante el apply — pero real; auto-flush por threshold y
mantenimiento de fondo la abren). El prototype del spike **RESPETA** ERR-010
(usa `batch_insert_with_opts`, UN guard L750, mismo que `insert`/`flush`).
Fix (envolver el apply del commit en `insert_lock`) es cambio `src/` prod con
tradeoff de serialización de commits → **fuera de este spike**; hallazgo
colateral para el lead (candidato a fila FIND nueva, no creada acá por
contrato).

### What the always-on gate detects — and what it cannot

The gate runs on push (`src/**`, `vantadb-python/**`, `benchmarks/**`, `Cargo.toml`/`Cargo.lock`) and via `workflow_dispatch`, comparing the median of 3 runs against `benchmarks/python_baseline.json`. Cross-VM spread measured on identical code (FIND-232, 2026-10-03, profile 10000/1000; runs 37088714140 / 37089421873 / 37089581213) is **1.7x–2.4x** on key metrics (`insert.p99` 16.8x) — GitHub rotates runner hardware, so the bands are calibrated to that noise floor:

| Family | Warn | Block |
| :--- | :--- | :--- |
| stable (`insert`, `rebuild`, `query_vector`) | >25% | >200% (≥3x) |
| quarantined (`query_hybrid`, `query_text`) | >15% | >300% **and** >0.5 ms absolute |
| `insert.p99_ms` | relative (warn only) | absolute: ≥100 ms |

The gate therefore detects **collapses (≥3x)**, not fine regressions (<2-3x). A profile mismatch (`insert.total_records` ≠ baseline) refuses to compare (fail-closed). For the fine signal in a controlled environment, use `cargo bench -p vantadb --bench canonical_p99` vs the baseline in §11.

### Same-job A/B (opt-in) — the fine-signal instrument

Dispatch the workflow with `ab_ref` set: wheel A is built from `ab_ref` and wheel B from the triggering ref **in the same job** (the machine factor cancels), then 3 alternated pairs `(A_i, B_i)` run — alternation cancels the warm-up ramp every job shows (adjacent-run deltas −1.2%..−22% on identical code, measured from the 2026-10-03 run logs) — and `compare_baseline.py --ab-runs` gates on the **median of the paired ratios**.

```bash
# A/B vs a ref (typically the commit that generated the current baseline):
gh workflow run perf-bench.yml --ref develop -f ab_ref=<ref-or-sha> -f size=10000 -f queries=1000 -f dim=128
gh run watch <run-id> --exit-status

# Calibration (same code on both sides — the measured deltas ARE the noise floor):
gh workflow run perf-bench.yml --ref develop -f ab_ref=$(git rev-parse HEAD)
```

- **Bands (provisional):** warn >15% / block >50% (median of paired ratios). `insert.p99` warns but never blocks (fsync jitter, 16.8x cross-VM). Calibrate the bands with the same-SHA dispatch above and tighten them with the measured noise floor (same protocol FIND-232 used).
- **Evidence per run:** every metric delta prints in the step log (`[ab] section.metric: B … vs A … (median delta …)`); artifact `vanta-benchmark-ab-results` carries side A's median.
- **Cost:** ~+5-9 min per invocation (2 wheel builds + 3 extra runs + wheel swaps) — opt-in only; the push gate stays ~4.5 min (measured, run 37089421873: rust-setup 1.1 min + wheel 0.7 min + bench 2.4 min).

### What this measures — and what it does not

Retrieval **quality** on a real text corpus: **`recall@k` against human relevance judgments (qrels)** with MTEB/TREC semantics — `recall@k = |top-k ∩ relevant| / |relevant|`, averaged over queries — plus **nDCG@10**, MTEB's main retrieval metric (MTEB paper §3.2, [arXiv:2210.07316](https://arxiv.org/abs/2210.07316)). Every engine retrieves over the **same embeddings** (all-MiniLM-L6-v2, mean-pool + L2 norm, 384d, max_seq 256, local ONNX export of rev `1110a24`), so the comparison isolates the retrieval/index layer, not the model.

- **Not comparable with:** §2 / §7 / §8 (different datasets and metrics), `competitive_bench.py` (`recall_at_k` there = fidelity of approximate search vs exact kNN on vector datasets — this section also reports that, as `index-recall`), and MTEB leaderboard values (different runtime/export; values here are pipeline-specific).
- **Both engines are exact on this corpus.** sqlite-vec (vec0) is a brute-force scan; VantaDB routes to its **flat exact scan** at this size — `flat_threshold` defaults to 10,000 nodes (`src/config.rs:347`, `VANTADB_FLAT_THRESHOLD` unset in this run) and `use_flat_search()` picks the flat path when `nodes.len() <= threshold` (`src/index/search/neighbors.rs`). `index-recall` = 1.0 is therefore expected by construction for both; the qrels recall they reach is the retrieval-quality ceiling of the declared embedding + ranking stack, not an ANN-fidelity result.

#### 22.3.1 La escala medida: 25 000 × 1536d, y por que no es la del plan

La escala del plan es **100 000 × 1536d**. En esta maquina **cabe** (el intento
anterior murio con `os error 1450` por culpa del *commit charge* al limite con
3 agentes compilando; aqui no habia ninguno), pero **no es affordable con el
protocolo completo**: el `insert` de 100k mide **~35-40 min por invocacion** y
el grupo de criterion del bench son 1000 queries × 10 muestras (≈ 10-20 min
mas) ⇒ **~6 h** para las 6 invocaciones intercaladas, y las 6 son las que
exige el plan (3 corridas por variante, mediana).

La escala medida es **25 000 × 1536d**, y la eleccion **no es arbitraria**:

1. **25 000 > `flat_threshold` (10 000) ⇒ el indice usa el camino HNSW (ANN), el
   mismo que ejercita el dataset canonico de 100k.** El motor enruta a
   **barrido plano (fuerza bruta)** cuando `nodes.len() <= flat_threshold`
   (`src/index/search/neighbors.rs:57`, `use_flat_search`), y
   `Config::default()` fija ese umbral en **10 000** (`src/config.rs:359`), que
   `StorageEngine::open` propaga al indice (`src/storage/engine/init.rs:462`).
   **Por tanto 10 000 y 5 000 —las dos escalas de reserva que se habían
   propuesto— son invalidas para esta comparacion**: miden un barrido sobre
   *todos* los vectores, que es otro workload, no el camino ANN que mide el
   dataset canonico. Lo mismo invalida las cifras de **2 000 × 1536d** publicadas
   anteriormente en esta seccion (estaban en el regimen plano).
2. **Los artifacts caben en el page cache** (~450 MB: WAL + vstore + imagen
   HNSW) ⇒ la medicion es de **CPU**, que es lo que el cifrado cambia, no de la
   E/S de la maquina.
3. **En el regimen HNSW el coste por query del cifrado lo fija `ef_search`**
   (los candidatos que visita el recorrido), **no `n`**: el coste del
   descifrado por candidato es el mismo a 25k y a 100k, ⇒ **el delta del
   regimen HNSW no puede colapsar a 0** al subir a 100k. Lo que **no** se ha
   medido es su **valor exacto** a la escala canonica (§22.3.5).

y la misma escala**. El baseline de **§11 (p99 4,9987 ms, 2026-09-25)** es el
bench **in-memory** (`canonical_p99`): con y sin la feature `encryption` mediria
**exactamente lo mismo**, asi que **no puede servir de umbral del coste

estable en esta maquina**: queda como pregunta abierta, no como cifra.

busqueda (§22.3.4).

#### 22.3.4 Lectura (el cuello de botella y el cambio de diseno)
1. **El problema es el camino de lectura, y es estructural, no de CPU.** El
   envelope del VantaFile es **por nodo**
   (`src/storage/vfile_crypto.rs::seal_node`), asi que el store cifrado
   **no puede devolver una vista prestada** del `mmap` — el plaintext es
   `Cow::Borrowed` sobre el mapping (`src/index_port.rs:86`), el cifrado tiene
   que **materializar**, y lo hace **varias** veces por candidato:
   `read_record_bytes` copia el ciphertext del mapping a un `Vec`
   (`src/storage/vfile.rs:997`), `open_node` lo descifra en otro `Vec`
   (`src/storage/vfile_crypto.rs:198`), `AlignedBlob::from_bytes` lo copia
   una tercera vez a un buffer alineado, `read_full_vector` reconstruye el
   `Vec<f32>` y `read_header` parseaba la cabecera copiando el payload
   entero. Un probe del **Paso 0** los midio en **5 copias por candidato** en
   cache fria (**1** con la cache caliente) y los reduzco a **3**: el
   ciphertext **se presta** del mapping, `read_header` parsea la cabecera *in
   situ*, `read_full_vector` paso de un bucle de 1536 iteraciones a un
   `memcpy` (`align_to::<f32>()`), y la cache de **una** entrada paso a una
   **LRU acotada** (`clamp(memory_limit/16, 16 MiB, 256 MiB)` por segmento,
   invalidada por escritura). **Lo que NO se puede quitar sin cambiar el
   formato es el 1 AEAD por candidato** (el envelope por nodo) ⇒ hace falta el
   **envelope por pagina** (que ademas es la unica forma de devolver el
   zero-copy, porque el `Cow<'_, [f32]>` del trait publico atado a `&self` no
   puede expresar una vista prestada de una cache). Con `ef_search = 100` son
   ~100 candidatos **por query**, y por eso el p99 se va.
2. **El camino de escritura no se penaliza**: el `insert` (+1,2 %) y el `flush`
   (−6,0 %) quedan **dentro del ruido** — ahi manda la E/S del WAL y del
   vstore, y el coste del envelope (µs) se pierde. El `flush` es **un** AEAD
   sobre ~150 MiB (la imagen HNSW entera): ahi el coste es **proporcional al
   tamaño**, no al numero de operaciones. El **cold start** (+47,3 %) si paga:
   descifra la **imagen HNSW entera** en cada open (sin mmap zero-copy), y el
   WAL se **valida entero** en cada open (`recover_valid_records_v4` descifra
   todos los frames).
3. **El cambio de diseno que hace falta** (el gate del plan ya lo anticipaba:
   *"superarlo es una señal de diseño, no algo que se absorba en silencio"*):
   **bajar la granularidad del envelope del VantaFile de "por nodo" a "por
   pagina"** (p. ej. 64 KiB) **y anadir una cache de paginas descifradas**
   (LRU). Con envelope por pagina el descifrado se amortiza sobre los ~10
   nodos de la pagina, y la pagina descifrada cacheada se vuelve a leer **sin
   copia** (vuelve el zero-copy). Para la **imagen HNSW**, un envelope por
   pagina permite descifrar en el arranque en frio solo las paginas que
   tocan, o descifrarlas en paralelo. Y para el **WAL**, truncarlo en el
   checkpoint (que `flush()` ya escribe) elimina el descifrado de todo el WAL
   en cada open. El diseño esta **ya especificado** en
   `docs/dev/architecture/design/2026-10-21-encryption-envelope-per-page.md`
   (commit `3c1c863`).
4. **Lo que NO se midio** y por que: (a) el dataset de **100k** del plan — cabe
   en RAM, pero el `insert` mide **~35-40 min por invocacion** y el grupo de
   criterion son 1000 queries × 10 muestras, o sea **~6 h** para el protocolo
   3+3 completo (§22.3.1): es una limitacion de **tiempo de maquina**, no de
   metodo; (b) el `p99` canonico *in-memory* de §11 en esta maquina — el bench
   canonico construye 100k × 1536 en RAM y no cabe junto al resto del trabajo
   en paralelo; (c) el **cold start** con la base ya abierta y sin `flush()`
   (la replay del WAL) — no hay API publica para "cerrar y reabrir sin
   checkpoint" y no se quiere anadir una.

> silencio); aqui va el mecanismo, con `file:line`.

(`Config::default()` = **10 000**, `src/config.rs:359`; el motor lo instala en

`src/index/search/neighbors.rs:57` — `nodes.len() <= threshold`):

| Escala | Camino de busqueda | De donde sale el vector | ¿Toca el ciphertext? |
| :--- | :--- | :--- | :--- |
| **≤ 10 000** | `flat_search` (`src/index/flat.rs:11`) | `node.vec_data`, **la copia en memoria** (el `vector_store` se recibe y se **ignora**, `src/index/flat.rs:122`) | **NO** |
| **> 10 000** | HNSW (`search_layer`) | `vs.read_full_vector(node.storage_offset, &header)` (`src/index/search/layer.rs:84` y `:257`) | **SI** — un AEAD + una materializacion **por candidato visitado** |

Consecuencia directa: **a 2 000 × 1536d (y a 10 000, y a 5 000) la busqueda es
un flat scan sobre las copias en memoria: no lee ni un byte del vstore, y por lo
tanto no descifra nada.** El delta de ±71 % / −14 % que media la tabla anterior
**no puede ser el coste del cifrado en la busqueda** — es ruido (y asi lo veia
la propia seccion: spread de +56 % a +200 % y un protocolo identico con el signo
contrario). Lo que esa tabla **si** media bien es todo lo que no es la
busqueda: el `insert` (que escribe el WAL, el vstore y la imagen), el `flush` y
el `cold start` (que si descifran).

**La escala que responde a la pregunta del plan tiene que estar en el regimen
HNSW**, y la mas pequena de ese regimen es **25 000 × 1536d**: por encima de
`flat_threshold` (10 000) —donde la busqueda **si** descifra— y por debajo de
lo que cabe con comodidad en el commit charge y en el **tiempo de maquina**
(§22.3.1). Ahi el p99 cifrado sale ya **~3-4x** el claro.

> **Lo que se puede afirmar (y lo que no) sobre el dataset canonico de 100k:**
> el coste de descifrado **por candidato** no depende de `n`, y el coste en claro
> **por candidato** tampoco ⇒ **el delta del regimen HNSW no puede colapsar a 0**
> al subir a 100k. Lo que **no** se ha medido es su **valor exacto** a esa
> escala: repetir el protocolo 3+3 a 100k son ~6 h de maquina (§22.3.1), y las
> cifras de §22.3.2 son a 25 000.

#### 22.4.4 Lo que el Paso 0 **quito** y lo que **queda**

**Lo que quito** (de 5 a **3** copias por candidato en cache fria; **1** con la cache caliente):

1. la copia del **ciphertext** a un `Vec`: ahora el ciphertext **se presta** del mapping
   (`read_record_bytes` devuelve `&[u8]`, `src/storage/vfile.rs:1180`);
2. la copia del **payload entero** para sacar los 64 B de cabecera: `read_header` parsea la
   cabecera **in situ**;
3. el bucle **byte a byte** de `read_full_vector` paso a `align_to::<f32>()` + `to_vec()` (un
   `memcpy`);
4. la cache de descifrado paso de **1 entrada** a una **LRU acotada**
   (`clamp(memory_limit/16, 16 MiB, 256 MiB)` por segmento) ⇒ un candidato caliente cuesta
   **0 AEAD** y **1 copia**.

**Lo que queda** (3 copias por candidato, cache fria) — y por que **no** se quita sin cambiar
el formato **o** la API publica:

1. **1 AEAD por candidato**: el envelope del VantaFile es **por nodo**
   (`seal_node`, `src/storage/vfile_crypto.rs:1121`) ⇒ quitarlo exige el **envelope por
   pagina**;
2. la copia del plaintext al **buffer alineado** (`AlignedBlob::from_bytes`);
3. la copia de los `words` al `Vec<f32>` (`to_vec()`): **estructural en el trait publico** —
   `VectorStoreRef::read_full_vector` devuelve `Option<Cow<'_, [f32]>>` con la vida atada a
   `&self` (`src/index_port.rs:86`), asi que **no puede expresar una vista prestada de una
   entrada de cache que se puede expulsar** (lo dice el propio codigo:
   `src/storage/vfile.rs:1276-1279`).

⇒ El coste que queda es **1 AEAD + 2 copias de ~6 KB por candidato**, y con `ef_search = 100`
son ~100 candidatos **por query**. **El 1 AEAD explica el resto del sobrecoste.**

⇒ **Lo que hace falta** es el **envelope por pagina** (p. ej. 64 KiB) + una cache LRU de
paginas descifradas: el AEAD se amortiza sobre los ~10 nodos de la pagina y la pagina
cacheada se vuelve a leer **sin copia** (vuelve el zero-copy) — **pero solo si el trait puede
expresar la vista prestada, y hoy no puede** ⇒ eso es un **breaking change del trait publico
`VectorStoreRef`**. El diseno esta especificado en
`docs/dev/architecture/design/2026-10-21-encryption-envelope-per-page.md` (commit `3c1c863`)
y revisado en `docs/dev/reviews/2026-10-21-encryption-envelope-por-pagina.md`.
