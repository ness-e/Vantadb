# Post-mortem: publicacion de VantaDB v0.9.0

> **Fecha:** 2026-10-20
> **Alcance:** desde el merge de `#238` (release PR con el bump a 0.9.0) hasta la
> verificacion final de los 15 registries.
> **Resultado final:** `ALL GREEN - release v0.9.0 verified` (15/15 registries, 14
> assets, `vanta-cli --version` -> `vanta-cli 0.9.0`).
> **Coste real:** el crate se publico **3 horas y 40 minutos** despues del merge del
> release PR, por 7 fallos encadenados. Ninguno fue detectado por un gate: todos
> aparecieron en produccion.

---

El release **se completo**, pero el camino fue: 3 publishes fallidos, 3 workflows
del fan-out en rojo, 2 merges con bypass de admin, y 5 workflows de CI
re-ejecutados por fixes de ultima hora.

## 2. Los 7 fallos, en orden de aparicion

### F1 - `please provide a non-empty token` (crates.io)

**Sintoma.** `cargo publish` fallaba tras compilar el crate (2m22s):
```
error: failed to publish vantadb v0.9.0 to registry at https://crates.io
Caused by: please provide a non-empty token
```
(run 39368867477, job 118451918327)

**Causa raiz.** El step de publish definiia
`CARGO_REGISTRY_TOKEN: ${{ secrets.CARGO_REGISTRY_TOKEN }}` y **ese secret no
existia**. Cargo decide entre token y Trusted Publishing por la **PRESENCIA** de
la variable, no por su valor: definida aunque este vacia, cargo se salta el
intercambio OIDC y falla pidiendo un token que no existe. El `env` lo habia
reintroducido la consolidacion de workflows (PR #242); el workflow de v0.8.0
(original) no lo tenia, y por eso v0.8.0 publico bien.

**Arreglo.** Quitar la definicion de la variable (la ruta OIDC, que es la
probada) o garantizar que el secret existe y es no-vacio. Nunca ambas.

**Prevencion.** `release.yml` documenta el motivo en el propio `env`. Un cambio
que anade una linea de `env` a ese step debe re-verificar el publish en un
entorno con el secret real.

### F2 - `403 Forbidden: authentication failed` (crates.io)

**Sintoma.** Con el secret ya configurado:
```
Caused by: the remote server responded with an error (status 403 Forbidden):
authentication failed
```
(run 39377761363)

**Causa raiz.** El token de crates.io no lo acepta para publicar. **No se pudo
aislar la causa desde fuera**: la API de crates.io responde 403 incluso a
endpoints publicos sin token, y `cargo owner --list` **no autentica** (lee el
fichero estatico de owners del indice git) - ver la seccion 3.

**Arreglo.** Volver a Trusted Publishing (OIDC) para crates.io, que es lo que
funciono para 0.8.0 (`trustpub_data.run_id = 37045089945`). El secret del
token **se conserva** en el repo para el primer publish de `vanta-memory`
(Trusted Publishing exige que el crate ya exista en crates.io).

**Prevencion.** `cargo owner --list` **no** es una prueba de token. Para
verificar un token de crates.io hay que hacer un publish real (o un
`cargo publish --dry-run` contra un crate de prueba).

### F3 - `403 E_STAGE_REQUIRED` (npm, primer publish de un paquete)

**Sintoma.**
```
npm error 403 Cannot publish "vantadb-node": this token can only publish to a
staging area, and "vantadb-node" does not exist yet. Create it first with a
direct-capable token, then use `npm stage publish`.
```

**Causa raiz.** Los tokens granulares de npm (2025+) publican a una *staging
area*. Para un paquete **que ya existe** funcionan (asi se publicaron
`vantadb` y `vantadb-wasm`), pero **no pueden crear** un paquete nuevo. npm
crea entonces el paquete con la version placeholder `0.0.0-stage` y deja la
version real pendiente de procesado.

**Arreglo.** Token con capacidad de *direct publish*. Con el nuevo token, el
propio `npm publish --access public` creo el paquete y subio la 0.9.0 (el
`0.0.0-stage` es un placeholder interno de npm; `dist-tags.latest` quedo en
`0.9.0`).

**Prevencion.** En la checklist de release: si el canal publica un paquete que
**aun no existe**, el token tiene que ser direct-capable.

### F4 - `clippy-preview ... detected conflict: 'bin/cargo-clippy'` (adapters PyPI)

**Sintoma.** Los 7 adapters no se publicaron:
```
error: failed to install component: 'clippy-preview-x86_64-unknown-linux-gnu',
detected conflict: 'bin/cargo-clippy'
error: metadata-generation-failed
```
(run 39380169218)

**Causa raiz.** `pip install -e vantadb-python` -> maturin -> cargo -> rustup lee
el `rust-toolchain.toml` de la raiz (`channel = "1.95.0"`,
`components = ["rustfmt", "clippy", "rust-src"]`) e intenta instalar el clippy de
1.95.0. Su proxy `bin/cargo-clippy` **ya esta ocupado** por el toolchain por
defecto (`stable`), que el action de arriba acaba de instalar. Dos toolchains
compiten por el mismo binario.

**Arreglo.** `RUSTUP_TOOLCHAIN: stable` en el step de dependencias: con la
variable fijada, rustup no consulta el `rust-toolchain.toml` y no hay conflicto.
Los demas workflows de release ya usaban `stable`, asi que esto ademas los
iguala.

**Prevencion.** Si un workflow usa `dtolnay/rust-toolchain` con un canal
distinto del pin del repo, y luego invoca `cargo`/`pip` dentro del repo, el
fichero `rust-toolchain.toml` gana y puede colisionar. Fijar `RUSTUP_TOOLCHAIN`
en el step lo hace explicito.

### F5 - `notarget vantadb-wasm@^0.9.0` (npm TS)

**Sintoma.** El paquete TS de npm no se publico; el smoke test TS-07 fallo:
```
npm error notarget No matching version found for vantadb-wasm@^0.9.0
```

**Causa raiz.** Carrera de propagacion: el tarball de `vantadb` depende de
`vantadb-wasm@^0.9.0`, que el **propio workflow** acababa de publicar **7
segundos** antes. La metadata de versiones de npm aun no lo servia, el install
fallo y el job se llevo por delante el publish del TS (no solo el test).

**Arreglo.** `scripts/smoke-pack.mjs` reintenta el install con backoff
(6 intentos, 15s -> 75s).

**Prevencion.** Un smoke test que resuelve una version **recien publicada** en
el mismo run es una carrera. Backoff, no fallo.

### F6 - `not a git repository` (job `fanout`)

**Sintoma.** El job `fanout` fallo en la primera llamada:
```
failed to run git: fatal: not a git repository (or any of the parent directories): .git
```
(run 39379695535)

**Causa raiz.** El job no hace checkout, asi que `gh workflow run` no puede
inferir el repositorio y aborta. Le faltaba `-R`.

**Arreglo.** `-R "${{ github.repository }}"` en las 7 llamadas.

**Nota de diseño.** Este job es **redundante mientras el tag se cree con el
PAT**: el push del tag ya dispara los 7 workflows (GitHub solo suprime los
eventos derivados cuando la autenticacion es `GITHUB_TOKEN`). Es el fallback
para ese caso, pero con el PAT su premise esta invertida: hoy exige el PAT
(`::error::RELEASE_PLZ_TOKEN is not set`) y aun asi duplica los runs.

### F7 - `ADR Gate (public API)` en rojo sobre un cambio de CI

**Sintoma.** El PR de fixes del path de release fallo el gate de ADR.

**Causa raiz.** El filtro de paths del gate es `vantadb-ts/` (todo el arbol), no
la superficie publica real: un **script de smoke test** no es API publica, pero
el gate lo trata como tal. Falso positivo.

**Arreglo inmediato.** Marcador `[no-adr]` con justificacion en el cuerpo del PR
(el gate lo lee en vivo de `pull_request.title`/`body`).

**Arreglo de fondo (PENDIENTE).** El filtro deberia mirar la superficie publica
real, no el arbol completo del paquete.

## 3. Fallos del propio instrumental de verificacion

Estos no son fallos del repo: son **falsos positivos de los metodos de
verificacion** usados durante el incident. Se documentan porque volveran a
aparecer:

| Metodo | Por que mentia | Metodo correcto |
|---|---|---|
| `cargo owner --list vantadb` | **No autentica**: lee el fichero estatico de owners del indice git. Dio "PASS" a un token que crates.io rechazaba con 403. | Un publish real, o `cargo publish --dry-run` con token contra un crate propio. |
| `gh api .../check-runs?per_page=100` | Trunca en 100. Un commit con 128 check-runs **ocultaba 5 checks requeridos** y hacia creer que faltaban. | Paginar hasta que la pagina venga incompleta. |
| `Invoke-WebRequest -Form` a PyPI | Devolvia 405 (enrutado) en vez de 400/403, parece un problema de token. | `requests` o `twine`, que es lo que usa el workflow. |
| `python -c "print(f'...')"` con comillas anidadas en PowerShell | SyntaxError por el shell, no por el codigo. | Fichero `.py`. |
| Verificar el `env` de un job leyendo su log | El dump de env **no incluye** las variables OIDC (`ACTIONS_ID_TOKEN_REQUEST_*`). | Mirar los permisos del job (`id-token: write`). |
| Confiar en `cargo owner --list` + `gh run watch` para un merge | El watchdog tiene deadline propio: aborta por reloj con los checks aun en curso. | Deadline holgado y log de por que aborta. |

Regla general que se deduce: **un token solo se da por valido si un publish
real lo acepta.** Ningun endpoint de lectura sirve como prueba.

## 4. Lo que casi sale mal y se salvan por poco

| Situacion | Por que era grave | Como se resolvio |
|---|---|---|
| El PR de fixes del release se mergeo desde una rama `develop` | `release-plz` solo publica si el **ultimo commit** de `main` pertenece a un PR cuya rama empieza por `release-plz-`. Un merge desde `develop` deja el release sin disparar. | Rama `release-plz-fix-cargo-token` (convencion documentada de release-plz para merges que arreglan el CI). |
| `develop` sin sincronizar con `main` | Un `develop -> main` futuro podria **reintroducir** lineas de `env` ya corregidas. | `develop` es ancestro de `main` (ff-only, sin divergencia): el sync es fast-forward, no hay rollback posible. Aun asi: **sincronizar `develop` tras cada release a `main`**. |
| Dos `if:` duplicados en el mismo job | GitHub rechaza el workflow entero ("This run likely failed because of a workflow file issue"). PyYAML **acepta duplicados** (gana el ultimo) y por eso la verificacion no lo vio. | Verificador con loader estricto que falla ante cualquier clave duplicada. |
| El semver check nunca habia completado en el repo | El job `release-plz-pr` solo se ejecuto con cambios reales el 2026-10-19: lo mataron a los 15 min con el check vivo a los 10m53s. El presupuesto de 30 min era una moneda al aire. | Medido (13m21s sin contension, 23m12s con la matriz en paralelo) -> 45 min. |
| 38 runs zombis de septiembre pidiendo runner | Explicaban la cola lenta de CI (1 job / 2 min). | Cancelados. |
| El gate de ADR marcaba scripts de test como API publica | Un PR de CI no podia mergearse sin bypass. | `[no-adr]` + fix de fondo pendiente. |

## 6. Checklist de pre-flight para el proximo release

1. **Los secrets existen y son no-vacios.** `gh secret list` y comprobar que
   ninguno esta vacio. Recordar: en `cargo publish` la *presencia* de
   `CARGO_REGISTRY_TOKEN` desactiva el OIDC.
2. **Canales que publican paquetes nuevos** necesitan token direct-capable
   (npm staging no crea paquetes).
3. **`rust-toolchain.toml` vs `dtolnay/rust-toolchain`:** si el workflow usa un
   canal distinto al pin, fijar `RUSTUP_TOOLCHAIN` en el step.
4. **El smoke test no debe resolver una version recien publicada** en el mismo
   run -> backoff.
5. **`gh workflow run` sin checkout -> `-R ${{ github.repository }}`.**
6. **Tag creado con PAT** -> los workflows de push se disparan solos: el fan-out
   duplica. Con `GITHUB_TOKEN` -> el fan-out es imprescindible. Elegir uno y no
   los dos.
7. **La rama del PR de release empieza por `release-plz-`** si el PR debe
   disparar la publicacion.
8. **Verificar el token de crates.io con un publish real**, no con
   `cargo owner --list`.
9. **Sincronizar `develop` con `main`** despues del release (ff-only) para que
   un `develop -> main` futuro no revierta fixes de `main`.
10. **Ejecutar `pwsh scripts/verify-release.ps1 -Tag v<version> -Smoke`** al
    final: assets + registries + sha256 + `vanta-cli --version`.
