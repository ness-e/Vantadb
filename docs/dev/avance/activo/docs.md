### El gate de rustdoc no fallaba en local porque en Windows la superficie es otra (`FIND-769`)
- **Fecha:** 2026-11-26
- **Objetivo:** `FIND-763` cableó el gate de rustdoc y **en su primer run real falló** (run `45804272736`, `ab3dae37f`, exit **101**, `private_intra_doc_links` sobre `create_snapshot`) mientras la **misma orden** había sido medida en verde **dos veces** en local (`FIND-755` + reviewer). - **Resultado — cuál de las tres era:** **ninguna de las dos primeras.** (1) *toolchain*: **descartada**, los dos lados son `1.95.0` (`docs-gates.yml:546` → `rust-setup` exporta `RUSTUP_TOOLCHAIN`, `action.yml:85-92`; el log del run lo imprime; local `rustc 1.95.0 (59807616e 2026-04-14)`). (3) *árbol/superficie*: **confirmada**, con un discriminador que el ticket no listaba — **la cfg de plataforma**. El único sitio marcado vive en la doc de un `pub fn create_snapshot` **`#[cfg(unix)]`** (`src/storage/engine/mod.rs:1611`); en Windows ese ítem **no existe**, así que rustdoc nunca procesa su doc. **El instrumento local no mide las dos superficies de rustdoc: mide las del host.**

El cross-doc al target linux desde Windows tampoco es viable (`croaring-sys` exige `x86_64-linux-gnu-gcc`). Conclusión operativa: **el único entorno que vale para la superficie unix es el runner de CI**; en local se duplica el comando exacto (workspace, no `-p`) y no se extrapola su verde a los ítems unix-only.
