### X-MPL-01 — Identidad persistida de espacio de embedding y capacidades declaradas

- **Problema:** fallos silenciosos al intercambiar storage o embedders — igual dimensión con distinto modelo mezcla espacios sin error; un fallback que quite scope filtra datos y un namespace no soportado no debe ignorarse.
- **Contrato hipotético:** `EmbeddingIdentity { model, revision, dimension, metric }` y `BackendCapabilities`; entrada `OpenEmbeddingSpace { scope, expected_model_revision, dimension, metric, required_capabilities }` → `open_checked(...) -> Result<ValidatedSpace, SpaceError>` con salida `{ identity, generation, effective_capabilities }`; errores `UnknownLegacyIdentity/ModelMismatch/DimensionMismatch/UnsupportedFilter/UnsupportedScope/StorageFailure`. El identificador del espacio no cambia por update de contenido; cambiar de modelo requiere nueva generación, no reetiquetar vectores antiguos.
- **Fuente de evidencia:** `mempalace/backends/base.py:153-204,462-582` (`PalaceRef`, `EmbedderIdentity`, `validate_write_batch`, `BaseCollection`) [M1]; `mempalace/backends/rust_exact.py:141-199` (`_query_native` captura versión, hidrata y recomprueba — si cambia lanza `_SnapshotChanged`, no devuelve lote mezclado) [M2]. El principio útil: vincular vector y payload a una revisión.
- **Seam VantaDB:** `vanta-memory/src/core/record/l1_writer.rs:51-110` (writer/`EmbedFn` — solo calcula vectores, no declara identidad durable); `vanta-memory/src/core/record/l1_reader.rs:321-380` (`recall_candidates` ya admite vector opcional).
- **Acciones:** 1) inventariar validaciones/guards actuales del SDK; 2) unificar detección de capacidades; 3) lectura compatible de identidad (`UnknownLegacyIdentity` para legacy); 4) validar identidad al abrir y guard de escritura; 5) propagar errores tipados hasta el adaptador y reembedding explícito en generación nueva cuando corresponda.
- **Dependencias:** catálogo de modelos y formato persistido; X-MPL-02 la requiere al combinar espacios distintos; X-MPL-03 condiciona el reuso de embeddings a esta identidad + digest de contenido. Validar antes del primer write; publicar identidad con la generación correspondiente.
- **FMEA:** aceptar igual dimensión con distinto modelo → mezcla espacios; fallback que quite scope → filtra datos; defaults de health no prueban salud; cancelación no debe dejar identidad nueva con vectores viejos.
- **Criterios de aceptación:** modelo incompatible no modifica el índice; backend incapaz de namespace devuelve error; batch desalineado se rechaza antes de escribir; mismo tamaño/distinto modelo falla; escritura durante hidratación entrega una revisión consistente o conflicto — no falso «vacío»; contadores mismatch/conflict/fallback sin vectores ni texto en logs.
- **Criterio negativo:** igualdad de dimensión no demuestra igualdad de espacio; un fallback conserva filtros y verifica capabilities — nunca los quita.
- **Independencia:** extender metadata actual del SDK (preferida) o validación en adapter como primer mínimo; rollback desactiva la ruta nueva sin renombrar espacios ni eliminar generaciones previas retenidas.
- **No objetivos:** no portar Chroma ni copiar un ABC Python a Rust; no otro motor ni otro store por comodidad.

### X-MPL-02 — Piso de evidencia raw que ningún derivado excluye

- **Problema:** una abstracción incompleta no debe ocultar evidencia que sí existe; los closets upstream son señales de ranking, no fuente literal ni condición para llegar al drawer, y su ausencia degrada a drawer-only.
- **Contrato hipotético:** `recall_with_raw_floor(scope, query, budget, source_revision) -> Result<FloorRecall, RecallError>`; cada hit conserva `EvidencePointer { source_id, span, revision }` y clase `CandidateOrigin::Raw | Derived` dentro del presupuesto compartido; errores `RawUnavailable/UnsupportedScope/StaleReference/ProviderFailure` separados. «Piso» = ejecutar la ruta raw autorizada aun sin abstracción útil — no reservar slots ni prometer que todo raw entre al top-k.
- **Fuente de evidencia:** `mempalace/searcher/query.py:315-369` (`search_memories` con piso raw y closets) [M5]; `mempalace/convo_miner.py:78-158` (`_closet_boosts:106-158`, `file_conversation_exchange:78-158`) [M3].
- **Seam VantaDB:** `vanta-memory/src/core/conversation/l0_recorder.rs` (`record_turn:274`, `read_messages:378`); `assemble_with_recall` — `vanta-memory/src/context_engine/engine.rs:252-264`.
- **Acciones:** 1) mapear la ruta raw existente; 2) verificar permisos antes de ambos brazos; 3) conservar el puntero al texto; 4) explicar boosts; 5) integrar en el ensamblador bajo el presupuesto actual.
- **Dependencias:** retención L0, provenance, filtros y token estimator; L0 es dueño del original, jobs de sus derivados; recall es read-only y el assembler posee el contexto entregado; depende de X-MPL-01 solo al combinar espacios distintos; compatible con X-MPL-04 para hidratar chunks y X-MPL-03 para revisiones.
- **FMEA:** doble presupuesto y duplicación → raw y derived del mismo source no duplican presupuesto; ventanas que exponen otra sesión → permisos antes de ambos brazos; índice derivado stale → detección por revisión, excluir stale; boost de derivado viejo lleva a fuente nueva equivocada; preservar secretos literalmente sin política de borrado.
- **Criterios de aceptación:** derivado vacío o fallido no bloquea evidencia raw autorizada; referencia resuelve a revisión correcta; borrado no deja previews recuperables; denegación en raw no se elude vía derivado/closet.
- **Criterio negativo:** cancelación de un brazo se refleja como fallo/omitido — no «éxito sin evidencia»; la consulta no eleva drawers por encima del presupuesto del assembler; no se mezcla texto nuevo con score viejo (rechazo o reconsulta explícita si cambió la revisión).
- **Independencia:** migración aditiva de metadata/punteros con históricos `Unknown` — no rellenar span inventado; rollback desactiva el boost y mantiene la ruta raw actual y provenance; alternativa: instrumentar primero el recall actual o adapter de origen.
- **No objetivos:** no prohibir síntesis L1/persona ni prometer recall total; no replicar closets como nueva taxonomía.

### X-MPL-03 — Reindexación recuperable por fuente sin destruir primero

- **Problema:** una reingest parcial no debe perder la última evidencia válida; upstream escribe lotes nuevos antes de purgar stale y marca el conjunto incompleto con `chunk_total` — recuperación por re-mine, no delete-first.
- **Contrato hipotético:** `SourceImportGeneration { source, revision, stage }` e `ImportOutcome::PendingCleanup | Committed`; `plan_import(source_id, expected_revision, chunks) -> ImportPlan`; `commit_import(plan) -> Result<ImportReceipt, ImportError>` con recibo `Prepared/Published/CleanupPending`; errores `RevisionConflict/CancelledBeforePublish/PartialCleanup/StorageFailure` no intercambiables. La generación identifica revisión, no timestamp del último retry.
- **Fuente de evidencia:** `mempalace/palace/writes.py:1-140` (`_split_unchanged`/`_upsert` reutilizan embeddings sin cambios antes del purge) y `:150-227` (`write_file_drawers`, `StaleDrawerPurgeFailed:11-16`; docstring exige `mine_lock(source_file)` — no acreditado como lease durable multiproceso) [M4].
- **Seam VantaDB:** `vanta-memory/src/ingest/worker.rs:109-301` (`ingest_body:244-301` liga `merge::commit` a `WikiStore::get_page/put_page`; `execute:109-151` marca complete/fail después de escrituras por página); el puerto por registro es `Embedded::put(MemoryInput)` — `src/sdk/api/memory.rs:1223-1240` [V-publish-record]; `CandidatePage`/`CommitReport` — `vanta-memory/src/ingest/merge.rs:16-49` (páginas `wiki/...`, no reciben generación de fuente).
- **Acciones:** 1) revisar la atomicidad real de ingest; 2) registrar generación por fuente; 3) preparar nuevos fragmentos (staging); 4) publicar por revisión y retirar stale; 5) recuperar cleanup reanudable e invalidar derivados por referencias; reuso de embeddings solo con identidad de modelo (X-MPL-01) y digest de contenido.
- **Dependencias:** IDs estables y checkpoints; revisión esperada por escritor de la misma fuente — no lock global sobre todos los ingestors; no se acredita una operación SDK que publique fuente+chunks+relaciones como generación indivisible — la política de generación/cleanup es propuesta sobre los puertos existentes, no un nuevo WAL/scheduler.
- **FMEA:** marcador borrado antes de cleanup; retry que duplica; IDs que chocan; conservar temporalmente dos versiones confunde recall; generación vieja no puede borrar chunks de la nueva por matching solo de path.
- **Criterios de aceptación:** interrupción entre lotes deja evidencia legible; la siguiente pasada converge; purge fallido no aparece como importación completa; otro modo/fuente no se borra; cambio de modelo fuerza reembed; cleanup fallido aparece pendiente; métricas por fase/reuso/conflicto sin paths privados ni texto de chunks.
- **Criterio negativo:** antes de publicar, el fallo conserva la última generación válida; después, el fallo de cleanup no revierte la fuente vigente ni dice «todo borrado».
- **Independencia:** preferir extensión del ingestor existente; alternativa reingest completo por nueva generación; migración marca legacy sin generación como `Unknown` — nunca completo por contar filas; rollback pausa nuevos imports y conserva recibos/cleanup, no borra el último raw.
- **No objetivos:** no certificar crash safety sin pruebas; no copiar `chunk_total+1` literalmente ni `mine_lock` como garantía; no delete-first.

### X-MPL-04 — Handle lógico de evidencia con hidratación y retirada de proyecciones

- **Problema:** una herramienta devuelve un ID y otra debe leer/inspeccionar/borrar la misma unidad lógica sin exigir una fila parent ficticia — los parentless son representación válida (issue #2752), no pérdida; borrar por prefijo sin mapping destruye lo equivocado.
- **Contrato hipotético:** `enum EvidenceHandle { Source(String), PhysicalChunk(String) }`; `EvidenceView { source_id, revision, chunk_ids, completeness }`; `resolve_evidence(scope: AuthorizedScope, id: EvidenceHandle) -> Result<EvidenceView, ResolveError>`; `plan_withdrawal(view) -> Result<WithdrawalPlan, ResolveError>`; errores `NotAuthorized/NotFound` sin revelar existencia ajena, `MissingChunk/RevisionConflict/UnsupportedHandle/StorageFailure`. El recibo separa retirada lógica, eliminación del primario y cleanup pendiente de índices/resúmenes/previews.
- **Fuente de evidencia:** `mempalace/mcp_server/tools_write.py:99-139` (`_logical_chunk_group`/`_chunk_group_record`), `:489-625` (`tool_add_drawer` devuelve handle lógico y chunks), `:697-712` (`_delete_resolved_drawer` distingue handle y chunk físico) y `:1229-1251` (`tool_get_drawer` hidrata) [M10]; `mempalace/palace/closets.py:278-329` (`drawers_removed` trata derivados después del commit) [M11]; issue #2752.
- **Seam VantaDB:** `src/cli_handlers/index.rs` (auditoría) y detalle Studio; provenance y lectura L0 existentes (`source_message_ids`, `vanta-memory/src/core/record/l1_writer.rs`); recibos de ingest (`vanta-memory/src/ingest/merge.rs`). El delta es el contrato común unidad lógica/filas/proyecciones — no otro índice ni catálogo paralelo.
- **Acciones:** 1) inventariar IDs/relaciones actuales; 2) resolver read-only por ID+revisión bajo scope; 3) contadores separados fuente/chunks/filas/proyecciones; 4) recibo de retirada; 5) cleanup idempotente.
- **Dependencias:** X-MPL-03 para revisiones; X-MPL-02 usa la resolución; X-MPL-05/06 no son requisito; históricos sin mapping quedan `Unresolved` — no se agrupan adivinando sufijos; ingestor/SDK posee fuente y mapping, jobs poseen cleanup.
- **FMEA:** falta chunk → texto incompleto → estado `MissingChunk`, no concatenación exitosa; parentless correcto → falso positivo de auditoría → contar unidades explícitas; delete parcial → preview sensible → retirada lógica y job reanudable; dos fuentes con basename idéntico → cruce → ID canónico y scope antes de resolver; chunk nuevo entre resolver y retirar → replantear, no borrar por prefijo textual.
- **Criterios de aceptación:** leer handle devuelve orden correcto; retirar handle no toca otra fuente; retirar un chunk no destruye otro; retry converge; fallo de proyección permanece visible; observabilidad en cantidades/estados/códigos — no previews ni paths privados.
- **Criterio negativo:** la view no prueba que todos sus derivados estén borrados; `PhysicalChunk` no implica autorización para retirar todo el source; fallar cleanup no reautoriza la lectura; upstream `drawers_removed` no prueba transacción global ni eliminación del KG.
- **Independencia:** extender el inspector existente (preferida) o adapter de source para formatos antiguos; reindex solo de proyecciones afectadas; rollback oculta la view nueva pero conserva tombstones/recibos.
- **No objetivos:** no prometer purga de backups/clientes ni GDPR completo; no rediseñar los IDs de todo Vanta imitando sufijos upstream; rechazar borrar por rango/prefijo sin mapping.

### X-MPL-05 — Relevo temporal preciso sin doble vigencia accidental

- **Problema:** «el responsable era Ana; desde el día D es Luis» — dos operaciones separadas con fecha sin hora pueden dejar ambos hechos vigentes en D o cerrar el anterior sin publicar sucesor.
- **Contrato hipotético:** `FactHandover { old_id, expected_revision, successor: FactCandidate, boundary: ExplicitInstant, source_event_id }`; `plan_handover(request) -> Result<HandoverPlan, TemporalError>`; misma frontera `[start,end)` para ambos; errores `InvalidBoundary/UnknownTime/RevisionConflict/UnsupportedAtomicPublish/StorageFailure`. Fecha parcial se expande por contrato explícito; «desconocido» nunca se convierte en now; timestamp de conocimiento separado.
- **Fuente de evidencia:** `mempalace/knowledge_graph.py:285-314` (`_temporal_filter_sql`: fecha-only de inicio expande al inicio del día, fin al final; límite superior estricto) y `:464-730` (`add_triple`, `invalidate`, `supersede`: convierte la frontera a instante preciso compartido y cierra/abre dentro de `with conn`; degrada a add cuando no hay old abierto — no imponerlo como default Vanta) [M9].
- **Seam VantaDB:** `vanta-memory/src/core/record/l1_writer.rs` (`valid_at`/supersession ya materializados, `persist_planned` delete→put `:289-294` — atomicidad prerrequisito solo del modo mutante) y `vanta-memory/src/core/record/l1_dedup.rs`; extender las decisiones del escritor, no una segunda tabla de hechos ni grafo SQL.
- **Acciones:** 1) acordar precisión/extremos; 2) función pura de plan (dominio sin LLM); 3) diagnóstico sobre campos existentes; 4) publicación segura por el escritor bajo revisión; 5) filtro histórico/inspección solo si se aprueba.
- **Dependencias:** X-MPL-06 aporta clasificación temporal cuando exista; C6, C14; complementario a la temporalidad de Graphiti — no duplicar; política de cardinalidad por predicado (no todo objeto distinto es incompatible).
- **FMEA:** frontera ambigua → doble actual → precisión explícita; replay → sucesor duplicado → `source_event_id` estable; disputa multiobjeto → falsa contradicción → política de cardinalidad por predicado; dos relevos simultáneos con misma base → conflicto, no dos actuales silenciosos.
- **Criterios de aceptación:** instante anterior/exacto/posterior, llegada tardía, end-only desconocido, conflicto y fallo de publicación; logs de acción/conflicto sin nombres ni fechas personales.
- **Criterio negativo:** no cerrar el viejo si el sucesor no puede publicarse con la garantía acordada; cancelación antes del commit no cambia nada — después se informa `committed`, no rollback ficticio; el `with conn` upstream no acredita atomicidad de `persist_planned` delete→put.
- **Independencia:** alternativa preferida antes de migración temporal global: preservar dos versiones con `superseded_by` actual; legacy `Unknown` permanece `Unknown` — no backfill desde `filed_at`; reindex temporal solo si el filtro lo necesita; rollback detiene la nueva semántica sin fusionar ocurrencias históricas.
- **No objetivos:** no decidir verdad automáticamente, no afirmar bitemporalidad completa ni portar todo `KnowledgeGraph` por tener un método transaccional.

### X-MPL-06 — Preview de importación entre fuentes con conflictos explícitos

- **Problema:** consolidar memorias de dos perfiles o importar una copia histórica sin que un hecho importado reemplace silenciosamente el actual; distinto del refresh de una sola fuente (X-MPL-03) — la aprobación no congela el target.
- **Contrato hipotético:** `ImportPreview { source_revision, target_revision, plan_digest, additions, conflicts }`; `preview_import(input: ScopedImport) -> Result<ImportPreview, ImportError>`; `apply_preview(plan, decision: AuthorizedDecision) -> Result<ImportReceipt, ImportError>`; clasificación `IdentityConflict/Present/PolicyConflict` — contradicción vigente no es last-write-wins; errores `SourceChanged/TargetChanged/NotAuthorized/UnsupportedSchema`. Preview no escribe fuentes, no crea namespace ausente ni descarga embeddings.
- **Fuente de evidencia:** `mempalace/knowledge_graph.py:56-193` (`knowledge_graph_notice:56-74` advierte grafo legacy no leído; `open_graph:77-85` no crea archivo en lectura sin fuente; `import_graph_rows:94-193` abre source read-only, preview sobre copia en memoria, copia solo columnas declaradas, distingue present/conflicts/id_conflicts, commit solo con apply) [M12].
- **Seam VantaDB:** `vanta-memory/src/ingest/merge.rs` (`CandidatePage`/`CommitReport` — solo merge de páginas wiki, dominio distinto); puertos por unidad `Embedded::put` — `src/sdk/api/memory.rs:1223-1240` [V-publish-record] y `Embedded::add_edge` — `src/sdk/api/graph.rs:113-151` (escribe extremos secuencialmente, sin revisión de plan ni metadata arbitraria por arista).
- **Acciones:** 1) distinguir páginas wiki de registros/relaciones; 2) mapear IDs y fuentes por los puertos anteriores; 3) clasificar conflictos read-only; 4) plan versionado serializable con scope y decisiones aprobadas asociados; 5) aprobación humana; 6) apply que revalida ambas revisiones/digest (si cambian, preview nuevo) y recibo por unidad con relación pendiente; 7) reindex derivados solo de registros incorporados.
- **Dependencias:** X-MPL-01/X-MPL-03 (identidad/revisión); X-MPL-04 para resolver soportes; X-MPL-05 aporta clasificación temporal cuando exista — no bloquea el preview básico; C4, C10; esquemas no soportados se rechazan — no adivinar columnas ausentes como permiso o fecha cero; condicionada a caso aprobado de migración/fusión.
- **FMEA:** colisión de ID → overwrite → clasificación `IdentityConflict`; target cambia tras preview → aprobación stale → `TargetChanged`; source cambia mientras se lee → mezcla → revisión/digest; import de gold de eval → fuga → trazabilidad y exclusión del corpus de evaluación; fallo de `put` o de la segunda escritura de `add_edge` → no se anuncia como import completo — recibo por unidad y relación pendiente.
- **Criterios de aceptación:** mismo archivo rechazado, preview no crea destino, duplicado compatible, intervalo distinto, conflicto explícito y retry sin duplicado; telemetría solo cantidades/estados; no borrar fuente o memoria manual ajena; un `CommitReport.written` de wiki nunca se usa como prueba de fuente/grafo publicado.
- **Criterio negativo:** mismo ID con distinto contenido es conflicto — no last-write-wins; no inferir autorización de pertenencia al mismo equipo; no se acredita atomicidad ni CAS por las firmas `put`/`add_edge` — commit por unidad existente, nunca afirmar lote atómico por nombre.
- **Independencia:** alternativas registradas: preview en adapter para formato externo, export/import sin merge como primer mínimo, rechazo de fusión entre scopes no autorizados; rollback deshabilita apply — no elimina memorias importadas sin una retirada autorizada posterior.
- **No objetivos:** no crear ahora formato universal, política de resolución automática ni nuevo harness de evaluación; no portar SQLite backup ni otro migrador; no fusionar grafos por defecto.
