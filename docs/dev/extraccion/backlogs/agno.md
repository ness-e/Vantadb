## Fichas completas

> Expansión de cada candidata a partir del informe `agent-memory-2026-11-07/agno.md` (§Fichas A–E y §11.2). Todos los contratos son **hipotéticos**: nombres propuestos sobre tipos del adapter, no APIs existentes de VantaDB. La evidencia `archivo:líneas` cita el clone upstream fijado en `f45ccee8`; las rutas VantaDB requieren revalidación contra HEAD.

### X-AGN-01 — Consolidación como revisión condicionada, no borrado previo

- **Problema:** upstream hace `clear` seguido de upserts individuales sin transacción envolvente visible; un fallo intermedio deja reemplazo parcial y pérdida de evidencia. La consolidación debe ser una revisión condicionada, nunca limpiar fuentes antes del reemplazo.
- **Contrato hipotético:** `ConsolidationPlan { scope, source_ids, source_revisions, replacement, provenance }`; `plan_consolidation(scope, refs, replacement, op_id) -> Result<ConsolidationPlan, AdapterError>` y `apply_consolidation(plan, cancel) -> Result<MutationObservation, AdapterError>` con errores `StaleSources`, `ScopeDenied`, `UnsupportedAtomicApply`, `OutcomeUnknown`. El caller posee la propuesta; el worker/checkpoint posee la aplicación; cancelar la preparación no escribe y tras commit se consulta `op_id`, no se repite `clear`.
- **Fuente de evidencia (clone):** `libs/agno/agno/memory/manager.py:803-873` (`MemoryManager.optimize_memories`: clear seguido de bucle de upserts; la pérdida efectiva exige fallo y semántica del adapter, no se reprodujo); `libs/agno/agno/memory/strategies/summarize.py:44-120` (`SummarizeStrategy.optimize`: resume contenido y combina topics — la consolidación cambia identidad y puede perder granularidad).
- **Seam VantaDB:** `vanta-memory/src/context_engine/engine.rs` (`assemble`/`assemble_with_recall`), `vanta-memory/src/core/record/l1_dedup.rs` y `vanta-memory/src/core/record/l1_writer.rs::plan_write/persist_planned` (ya tienen merge, versiones y fuentes); scheduler/checkpoints para trabajo diferido. El plan se referencia por el checkpoint existente.
- **Acciones:**
  1. Inventariar fuentes y revisiones; registrar presupuesto.
  2. Generar la propuesta fuera del motor, con LLM opcional, fuera del lock.
  3. Validar alcance y revalidar revisiones antes de publicar.
  4. Publicar reemplazo y supersession con el mecanismo real del backend (atómico o con recuperación explícita); registrar recibo.
  5. Habilitar por caller; al desactivar, conservar fuentes/reemplazos e historial.
- **Dependencias:** revalidar dedup/supersession/compaction existentes; precisar atomicidad de aplicar consolidación sin bloquear inferencia (prerrequisito §4); X-AGN-02 autoriza el scope; X-AGN-05 emite el recibo; converge con C13 MutationReceipt (propuesto). Legado sin revisión no obtiene CAS ficticio.
- **FMEA:** crash entre clear y upsert → reemplazo parcial (prohibir clear-then-upsert); escritor concurrente borrado por una consolidación vieja → publicar solo sobre revisiones aún válidas; resumen tardío con revisión distinta → conflicto sin borrado; resumen que mezcla usuarios → scope de X-AGN-02; pérdida de evidencia → conservar originales o referencias.
- **Criterios de aceptación propuestos:** fallos entre etapas dejan fuente o reemplazo recuperable; revisión obsoleta no pisa datos nuevos; cada hecho consolidado conserva referencias a sus fuentes; cancelar no elimina originales; distinguir aplicado/conflicto/desconocido sin registrar contenidos sensibles.
- **Criterio negativo:** ninguna consolidación deja las fuentes borradas con el reemplazo ausente o parcial; una revisión obsoleta nunca sobrescribe datos más nuevos.
- **Independencia:** evaluable como delta sobre la compactación/dedup/supersession existentes; alternativa barata documentada: conservar originales y solo marcar sustitución. Abierto: garantía de grupo efectiva del backend.
- **No objetivos:** no sustituir el context assembly; no exigir LLM al storage; no reindexar hechos invariantes (los cambios de contenido/vector siguen la ruta existente sin anunciar proyección lista antes de tiempo).

### X-AGN-02 — Scope tipado y autorización de recurso antes de mutar

- **Problema:** compartir deliberadamente debe separarse de compartir por omisión. Upstream resuelve conflicto solo por `memory_id` sin condición de user: con DB compartida e ID ajeno conocido, el update puede mutar una fila de otro user y `clear_memory` borra global sin user. Un slug/namespace o el user de inserción no equivalen a ACL.
- **Contrato hipotético:** `MemoryScope { tenant, owner, audience, namespace }` (nombre conceptual — mapear a `RecallScope`/`RecallConfig`/`InjectionPolicy` y tenancy L1 existentes, no crear otro tipo); `resolve_scope(authenticated_actor, requested_scope, operation) -> Result<AuthorizedScope, AdapterError>` con errores `MissingOwner`, `ScopeDenied`, `LegacyUnmapped`. Owner obligatorio para memoria personal; audience explícita para compartir; agent/team pueden ser provenance sin ser ACL. La autorización cubre también el recurso existente por ID antes de update/delete/merge.
- **Fuente de evidencia (clone):** `libs/agno/agno/learn/stores/user_memory.py:57-149,930-934` (`UserMemoryStore`, `_build_memories_id`; agent/team son auditoría, no scopes privados); `libs/agno/agno/learn/stores/entity_memory.py:426-463` (`EntityMemoryStore.recall`); `libs/agno/agno/db/sqlite/sqlite.py:2699-2725,2849-2867` (SQLite acredita delete global; los demás drivers del issue son reporte, no auditoría propia). Motivada por issue #9983 (manager tool global; #9986 es corrección propuesta sin merge acreditado).
- **Seam VantaDB:** `vanta-memory/src/core/hooks/auto_recall.rs` (`RecallScope`, `InjectionPolicy`); sesiones/personas/escenas, filtros del retrieval y provenance existentes; mapping de identidad en `integrations/vantadb_shared` (adapter Python), no copiar AgentOS ni crear IAM.
- **Acciones:**
  1. Inventariar scopes y auth actuales.
  2. Definir el mapping de identidad del caller en el adapter (la identidad viene del host, nunca del texto LLM ni del DTO).
  3. Mapear audience a políticas existentes y aplicar filtros antes de retrieval y consolidación.
  4. Autorizar también el recurso existente por ID antes de update/delete/merge; detectar discrepancia actor/owner y rechazar antes del efecto.
  5. Resolver el legado sin owner por decisión explícita (sin mapping hasta decisión autorizada, nunca usuario global ni migración a público); registrar solo identidad/scope/decisión, no PII cruda.
- **Dependencias:** inventario de auth/scope actual; mapping de identidad del caller; la misma decisión aplica a recall y a write. X-AGN-04 depende de su scope; X-AGN-05 declara capacidades scoped.
- **FMEA:** `"default"` compartido en despliegue multiusuario → cruces entre tenants; namespace compartido confundido con público; agente originador confundido con lector autorizado; prompt injection que pide ampliar scope → rechazo por política externa; filtro posterior a top-k usado como sustituto de autorización previa (rechazado: el filtro post-retrieval no repara el envío previo); fallo de validación no altera el scope previo.
- **Criterios de aceptación propuestos:** mismo user local en tenants distintos no se cruza; compartir requiere acción trazable; borrado respeta audience y fuentes; recall y extracción usan el mismo scope validado; ID propio permite update autorizado; ID ajeno deniega sin cambio; ID inexistente distingue insert permitido de update no encontrado; verificado con wrapper autorizado y dos users compartiendo DB.
- **Criterio negativo:** un ID ajeno conocido no permite mutar la fila de otro user; `clear` no borra global sin condición de scope; ninguna configuración de cliente amplía privilegios.
- **Independencia:** puede existir sin LLM; es prerequisito de X-AGN-03/X-AGN-04/X-AGN-05. Una DB por cliente simplifica aislamiento pero multiplica gestión (alternativa documentada).
- **No objetivos:** no crear un sistema general de identidad ni framework multiagente; no trasladar el usuario global por defecto a un servicio multiusuario; desactivar el adapter no cambia la ACL del primario. Abierta: audience compartida por caso de producto.

### X-AGN-03 — Propuestas de memoria con decisión verificable

- **Problema:** upstream declara PROPOSE/HITL en el enum pero el store no lo soporta; una opción nominal no debe aparentar una barrera de aprobación donde solo hay extracción automática.
- **Contrato hipotético:** `MemoryProposal { evidence_ids, scope, operations, extractor_version, state }` almacenada fuera del recall de hechos; `decide(proposal_id, expected_revision, actor, decision, op_id) -> Result<ProposalOutcome, AdapterError>` idempotente con errores `StaleProposal`, `EvidenceChanged`, `AlreadyDecided`, `ScopeDenied`. Decisión y aplicación son operaciones diferenciadas; el rechazo no publica hecho; la cancelación de UI no revoca un commit confirmado.
- **Fuente de evidencia (clone):** `libs/agno/agno/learn/stores/user_memory.py:76-149` (`__post_init__`/`process`: PROPOSE/HITL declarados sin soporte en el store); `libs/agno/agno/db/schemas/memory.py:8-43` (`UserMemory` con input/feedback/agent/team).
- **Seam VantaDB:** provenance/supersession de `vanta-memory` + `vanta-memory/src/utils/task_checkpoint.rs` (guarda decisión/actor/revisión y referencia a recibo — estado de aprobación nuevo, no otro scheduler); aprobación en adapter o Studio existente.
- **Acciones:**
  1. Hacer explícita la capacidad HITL real (negociarla vía X-AGN-05).
  2. Persistir la propuesta sin incorporarla al recall de hechos.
  3. Resolver actor, comprobar evidencia/scope y revisión esperada.
  4. Aplicar por X-AGN-01 o por el write existente con clave idempotente.
  5. Devolver recibo vinculado a las fuentes; conservar relación decisión/recibo y permitir desactivar nuevas propuestas sin revertir commits.
- **Dependencias:** X-AGN-02 (scope) y X-AGN-05 (capacidades) son prerequisitos; X-AGN-01 solo para operaciones compuestas; checkpoints existentes guardan la decisión. Solo procede si el producto necesita aprobación de hechos.
- **FMEA:** prompt injection en hechos propuestos; doble aprobación/doble click → mismo `op_id` → mismo receipt; edición de fuentes después de aprobar → `EvidenceChanged` invalida; actor revocado → rechazo al aplicar aunque aprobara antes; fallo al notificar → resultado desconocido consultable por `op_id`, no reejecución del efecto; resumen LLM no prueba verdad.
- **Criterios de aceptación propuestos:** propuesta rechazada nunca entra a recall; retry no duplica memoria; aprobación sobre revisión vieja se invalida; audit distingue fuente, inferencia y actor; la evidencia cruda no se reemplaza por resumen; hechos antiguos nunca se marcan «aprobados» sin evidencia de quién los aprobó.
- **Criterio negativo:** una opción HITL no soportada por el backend no puede configurarse nominalmente; un rechazo no publica el hecho; una propuesta nunca se incorpora al recall sin decisión.
- **Independencia:** depende de X-AGN-02 y X-AGN-05; condicional a que el producto requiera aprobación de hechos (no se impone HITL a todo write).
- **No objetivos:** no imponer HITL a todo write ni portar el ciclo de agentes; no migrar hechos antiguos a «aprobados». Abierto: qué operaciones requieren intervención humana.

### X-AGN-04 — Directorio de entidades con cobertura explícita

- **Problema:** un agente debe distinguir «entidad no encontrada» de «directorio no explorado por presupuesto», sin volcar todas las fichas al modelo; un match léxico no prueba identidad real.
- **Contrato hipotético:** `EntityRecallView { scope, source_revision, directory_refs, expanded_refs, truncated, continuation }`; `read_entity_view(scope, query, cursor) -> Result<EntityRecallView, AdapterError>` con errores `ScopeDenied`, `StaleCursor`, `InvalidEntityRef`. El cursor está ligado a revisión/scope; el caller posee el cursor y el motor la lectura (no hay commit externo por recall).
- **Fuente de evidencia (clone):** `libs/agno/agno/learn/stores/entity_memory.py:426-500` (`EntityMemoryStore.recall`: cap+1 revela truncamiento; expansión por identidad precede a matching y búsqueda léxica intercalada), `:1300-1322` (`_novel_facts`).
- **Seam VantaDB:** `vanta-memory/src/context_engine/engine.rs::assemble_with_recall`, `vanta-memory/src/core/hooks/auto_recall.rs::RecallConfig` y metadata/provenance L1 — agregar cobertura del directorio al reporte contextual existente, no otro BM25 ni tabla paralela de hechos.
- **Acciones:**
  1. Mapear identidad/tipo/aliases existentes.
  2. Listar con límite y señal de truncamiento cap/cap+1.
  3. Expandir solo IDs autorizados por scope.
  4. Ensamblar con el budget global existente y reportar omitidos.
  5. Mantener la vista derivable y desactivable sin borrar hechos (rollback quita vista y mantiene retrieval existente).
- **Dependencias:** X-AGN-02 para scope; versión/paginación existentes; assembler existente; X-AGN-01 debe invalidar referencias sustituidas. Independiente de X-AGN-03 y de inferencia LLM.
- **FMEA:** directorio truncado → falso negativo → marcar parcial; alias ambiguo → mezcla de personas → referencias tipadas y evidencia separada; borrado concurrente → expansión ausente → `StaleCursor` o vista parcial detectable, nunca ficha inventada; cambios de aliases invalidan cursor, no reescriben hechos; revalidar scope antes de expandir.
- **Criterios de aceptación propuestos:** cap exacto y cap+1 se distinguen; archivado no se expande en el modo declarado; mismo nombre/tipos distintos no se conflan; entidad exacta se expande; alias ambiguo no une personas; cursor stale no da negativo global; cancelación devuelve error o vista completa declarada.
- **Criterio negativo:** un directorio truncado nunca se reporta como «entidad inexistente»; un match léxico nunca se presenta como identidad confirmada.
- **Independencia:** sin índice nuevo ni migración; requiere X-AGN-02. Alternativas documentadas: lista exhaustiva solo para conjuntos pequeños; retrieval puro evita coste de directorio pero no sustenta negativos sobre cobertura.
- **No objetivos:** no crear un entity runtime nuevo; no resolver verdad ontológica con un LLM; no sustituir dedup/supersession existentes ni importar todo el grafo de entidades y sus heurísticas. Abiertos: identidad canónica externa y resolución de ambigüedad.

### X-AGN-05 — Capacidades negociadas y recibo de mutación

- **Problema:** el adapter puede declarar HITL/async/clear-scoped que el método elegido no soporta, o devolver un ID aunque nada haya persistido (upstream devuelve UUID aunque una coroutine no awaited nunca escribió); el ID no certifica persistencia y un warning ignorado no debe contarse como soporte.
- **Contrato hipotético:** `MutationCapability { scoped_delete, conditional_replace, proposal_decision }` declarada por adapter y `MutationReceipt { op_id, committed_refs, outcome }`; `negotiate_memory(backend_caps, required) -> Result<CapabilityAgreement, AdapterError>`; `Unsupported`, `NotApplied`, `OutcomeUnknown`, `ScopeDenied` como resultados distintos. Mantener `Accepted`/`Applied`/`Durable`/`Visibility` como observaciones independientes y `Unknown` donde no existe evidencia — un UUID retornado no llena esas dimensiones.
- **Fuente de evidencia (clone):** `libs/agno/agno/learn/stores/user_memory.py:76-149`; `libs/agno/agno/memory/manager.py:220-247,576-585` (`add_user_memory`/`_upsert_db_memory`: retorna ID y llama método sin await, convirtiendo excepciones en texto). Issues #11143 (CRUD sync con AsyncBaseDb sin await; PR #11154 mencionada sin merge acreditado) y #9983.
- **Seam VantaDB:** `integrations/vantadb_shared/__init__.py` (validar capacidades al conectar el binding Python) y `vanta-memory/src/utils/task_checkpoint.rs` (`TaskCheckpointManager` para seguimiento); `WriteReceipt` existente en `src/attestation.rs` (vincula contenido/versión/store/WAL con SHA-256 y relectura — integridad, no firma ni prueba de derivados/commit remoto).
- **Acciones:**
  1. Inventariar métodos/endpoints del binding.
  2. Declarar soporte real y rechazar al inicio combinaciones inválidas, antes del write.
  3. Esperar la frontera del backend y emitir recibo verificable mapeado al SDK.
  4. Versionar el formato de capacidades por adapter con observaciones en actividad/checkpoint.
  5. Declarar si update autoriza owner, si solo hace upsert por ID y cómo distingue ID propio/ajeno/inexistente.
- **Dependencias:** X-AGN-02 para operaciones scoped (la autorización de recurso se exige en X-AGN-02, no se infiere de un recibo de éxito); X-AGN-01/X-AGN-03 consumen los recibos; ownership del intento en el host; persistencia en el backend. Legacy `Unknown`; desactivar la negociación no permite fingir atomicidad.
- **FMEA:** coroutine no awaited → ID sin write → error de capacidad temprano; timeout después de commit → retry duplicado → `op_id`; feature no soportada → warning ignorado → rechazo explícito; upsert por ID ajeno sin ownership → modificación cruzada → autorización de recurso previa; wrapper sync sobre async → coroutine sin await → ID sin dato (la negociación rechaza la combinación y no reintenta ciegamente); estado aplicado + notificación cancelada → cliente cree rollback → duplicación (inspeccionar `op_id`/recibo sin reejecutar el efecto). Observar código/ID/estado, no texto.
- **Criterios de aceptación propuestos:** `unsupported` no cambia datos; error operativo no se devuelve como éxito; `op_id` repetido no genera identidad nueva; `close` no borra; combinación válida conserva frontera de commit; cancelación posterior al commit conserva la observación conocida. Métricas: códigos de decisión/conflicto/capacidades y tiempos por fase — sin payload, topics/PII ni prompts por defecto.
- **Criterio negativo:** un UUID retornado sin persistencia no se presenta como commit; una capacidad no soportada nunca degrada a warning ignorado; cancelar después de commit no convierte éxito en «no aplicado» ni revierte efectos.
- **Independencia:** la comprobación estática del adapter suele bastar (alternativa documentada: no construir un descubridor dinámico universal ni bucle de retries dentro del storage). Abierto: si el proveedor ofrece consulta real por `op_id`.
- **No objetivos:** no prometer exactly-once de sistemas externos; no crear nuevo worker ni proveedor LLM; no envolver todos los métodos sync con async ficticio; no migrar IDs de hechos.
