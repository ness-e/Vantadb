### X-OAP-01 — Rewind de intento condicionado a propiedad del sufijo

- **Problema:** un retry no puede deshacer escrituras ajenas por semejanza de contenido ni interpretar cancelación como rollback. La comprobación de propiedad debe gobernar la mutación bajo la frontera de escritura real, no ser una lectura previa seguida de pops públicos.
- **Contrato hipotético (tipos propuestos):** `rewind_attempt(s: &AuthorizedSession, req: AttemptSuffix, cancel: &CancelToken) -> Result<RewindOutcome, SessionMutationError>`; `AttemptSuffix { session, attempt_id, expected_tail, owned_ids }` (expected revision y op_id solo en el envelope del adapter); `RewindOutcome { removed, conflict, outcome_unknown }`. Errores propuestos: `ScopeDenied`, `StaleGeneration`, `NotOwner`, `UnsupportedAtomicMutation`, `OutcomeUnknown`; no se infiere rollback desde timeout.
- **Fuente de evidencia:** `src/agents/run_internal/session_persistence.py:1873-1962` (O5: verificación de sufijo y restauración best-effort, llamadas separadas sin atomicidad acreditada) · `src/agents/memory/sqlite_session.py:447-520` (O4: pop validado dentro de la transacción).
- **Seam VantaDB:** `vanta-memory/src/core/record/l1_writer.rs::persist_planned/log_and_mark` (NV4), `vanta-memory/src/utils/task_checkpoint.rs::TaskCheckpointManager`, locks por sesión/retry del worker existente (V2).
- **Acciones:**
  1. Inventariar si el host ya conserva identidad de intento y turnos.
  2. Separar items históricos de los aportados por la ejecución; contenido duplicado no es una identidad.
  3. Si se necesita rollback, definir compare/remove bajo la frontera de escritura real; no componer lectura y pops públicos como CAS inexistente.
  4. Devolver conflicto sin eliminar items ajenos; preservar errores de restauración en diagnósticos autorizados.
  5. Secuencia propuesta: inventariar ID de intento → registrar ownership en checkpoint → validar scope/revisión → mutar bajo frontera real → emitir observación.
- **Dependencias:** ID estable, orden total por sesión, operación backend apropiada y semántica clara de timeout/cancelación; locks por sesión/retry del worker existente. Migración: legacy sin ownership no rebobina por parecido de texto; no reindex. Rollback de la propuesta: quitar API/adapter no borra historial; conflicto no elimina.
- **FMEA:** interleaving — otro escritor añade entre comprobar y retirar → la comprobación debe gobernar la mutación, no solo una lectura anterior (conflicto por revisión); repetición legítima — dos turnos dicen lo mismo y se borra el antiguo → la propiedad no se deduce del texto, se usan IDs de ownership; cancelación tras commit — retry vuelve a añadir contenido aplicado → conservar resultado conocido/desconocido e idempotencia existente.
- **Criterios de aceptación propuestos:** solo se elimina el sufijo del intento esperado; conflicto deja intacta la historia superviviente; cancelación postcommit conserva outcome conocido/desconocido. Observabilidad: IDs/revisión/error sin payload.
- **Criterio negativo:** un backend sin la garantía necesaria la declara; no se anuncia exactly-once ni rollback fuerte con helpers best-effort. Si el backend no ofrece frontera suficiente, no se ofrece rewind — abortar es más seguro.
- **Independencia:** útil para retry de ingesta/captura sin requerir X-OAP-02 (compaction).
- **No objetivos:** portar `RunState` entero, handoffs ni conversaciones OpenAI; no dedup nuevo — la propiedad vive en el adapter.

### X-OAP-02 — Publicación versionada de compaction con originales preservados

- **Problema:** reemplazar contexto no debe vaciar historial durable si falla el guardado, ni sobreescribir una generación que cambió mientras se resumía. Clear+add compensado no es una frontera atómica.
- **Contrato hipotético (tipos propuestos):** `prepare_compaction(s: &AuthorizedSession, snap: ContextSnapshot, replacement: Vec<ContextItem>) -> Result<CompactionCommit, CompactionError>` y `publish_compaction(s: &AuthorizedSession, commit: CompactionCommit, cancel: &CancelToken) -> Result<CompactionPublish, CompactionError>`; `CompactionCommit { source_generation, replacement, preserved_refs }`, `CompactionPublish { applied_generation, conflict }`. La capacidad atómica se resuelve sobre el tipo inmediato del wrapper para no saltarse transformaciones como cifrado.
- **Fuente de evidencia:** `src/agents/memory/openai_responses_compaction_session.py:559-650` (O6: reemplazo y restauración ante excepción/cancelación, hook resuelto en tipo inmediato; fallback clear/add+restore no es ACID universal) · `:90-184` (O19: constructor/defaults — `model`, modo auto, hook 10+ candidatos; defaults del pin, no recomendaciones Vanta).
- **Seam VantaDB:** `vanta-memory/src/context_engine/engine.rs::assemble_with_recall` (NV3), `vanta-memory/src/context_engine/spill.rs` (spill reversible que conserva originales), `IntegratedContext`/`CompactionReport`.
- **Acciones:**
  1. Revisar integración actual entre assembler, spill y persistencia.
  2. Mantener cómputo puro fuera del commit; validar que el snapshot sigue siendo aplicable justo al publicar.
  3. Reutilizar transacción/batch existente para el puntero visible; fallback solo con garantías y restauración explícitas.
  4. Publicar éxito después de confirmar el backend, incluso si la notificación al llamador termina cancelada.
  5. Secuencia propuesta: snapshot → prepare fuera del lock → revalidar → guardar originals/spill → publicar puntero/reemplazo → reportar.
- **Dependencias:** revisión monotónica, retención de originales, autorización, contrato de spill y marcadores de compactación existentes. Migración: versionar refs/envelope, no reindex si contenido/vector invariantes. Rollback: desactivar nuevas compactaciones, originals preservados; no pisa generación nueva.
- **FMEA:** resumen tardío — reemplaza mensajes posteriores → condicionar a generación/identidad de entrada y devolver `StaleGeneration`; clear/add parcial — sesión queda vacía → preferir frontera atómica real antes que confiar en compensación no durable; restauración cancelada — reparación en background no asentada permite leer vacío → definir propiedad y finalización explícitas de la recuperación.
- **Criterios de aceptación propuestos:** historial previo o reemplazo válido, nunca vacío accidental anunciado como éxito; los originales siguen siendo recuperables. Contexto: preservar tool-call/result, prefijo protegido y presupuesto compartido; no duplicar reglas del assembler. Observabilidad: generación/refs/etapas sin texto.
- **Criterio negativo:** un corte entre pasos no se anuncia como éxito; no se salta el wrapper cifrado para alcanzar atomicidad; no se declara durabilidad más fuerte que la del backend.
- **Independencia:** no requiere eliminación de sufijo ni la API de rewind X-OAP-01.
- **No objetivos:** usar el endpoint de compactación OpenAI como requisito; nuevos prompts, thresholds o política de retención; no crear un summarizer nuevo.

### X-OAP-03 — Vista de handoff autorizada separada del historial persistido

- **Problema:** un triage que pasa a especialista con contexto mínimo autorizado debe conservar evidencia cruda para auditoría; filtrar solo `input_items` no redacta nested history y los items ya streameados no se retiran.
- **Contrato hipotético (tipos propuestos):** `project_handoff(actor: &Actor, target: AgentRef, history: &ContextSnapshot, policy: &InjectionPolicy) -> Result<HandoffView, HandoffViewError>`; salida refs/generación/omitidos. Errores propuestos: `ScopeDenied`, `UnsupportedRemoteFilter`, `StaleGeneration`, `InvalidToolGroup`.
- **Fuente de evidencia:** `src/agents/handoffs/__init__.py:72-179` (O10: `HandoffInputData` separa `input_history`, `pre_handoff_items`, `new_items` e `input_items`; el filtro actúa sobre la próxima vista preservando `new_items` en Session; server-managed conversations no soporta esos filtros).
- **Seam VantaDB:** `vanta-memory/src/context_engine/engine.rs::assemble_with_recall` (NV3), `vanta-memory/src/core/hooks/auto_recall.rs::InjectionPolicy` (NV4) — decisión de compartición/revisiones adjunta al assembler existente, no retrieval ni transferencia de permisos desde el modelo.
- **Acciones:**
  1. Identificar recursos → autorizar → seleccionar/redactar refs → verificar grupos call/result → registrar decisión → entregar.
  2. Adjuntar la decisión de compartición al assembler existente con refs autorizadas + vista, originales intactos.
  3. No borrar raw; legado sin recibo de entrega significa `Unknown`.
  4. Rollback quita la proyección, no los hechos; sesión remota no soportada produce error explícito, no filtrado ficticio.
- **Dependencias:** provenance/budget existentes; X-OAP-02 solo si se compacta; independiente de inferencia y de framework de agentes.
- **FMEA:** nested ignora la vista redactada → fuga de contexto → detectar source fields incluidos y bloquear nested incompatible; stream previo no revocable → filtrar antes de emitir, no prometer borrado retroactivo.
- **Criterios de aceptación propuestos:** el destino normal solo ve autorizados; revocación/sesión remota no soportada produce error explícito; tool-result huérfano rechazado; métricas de IDs/counts/decisiones sin payload.
- **Criterio negativo:** vista opt-in; donde no hay soporte de filtrado se devuelve error explícito — nunca un filtrado ficticio que presente evidencia incompleta como completa.
- **Independencia:** vista opt-in; no depende de rewind, compaction ni de inferencia; X-OAP-02 solo entra si la publicación dispara compaction.
- **No objetivos:** no SDK de handoff en Rust; no transcript completo como default (expone más) ni «solo resumen» (oculta fuentes). Abierto: quién posee la redacción y qué transports permiten verificar entrega.

### X-OAP-04 — Publicación recuperable de resultados de herramientas

- **Problema:** una herramienta pudo aplicar efecto (cobro, envío) antes de que falle `add_items`; reanudar no puede reejecutar el efecto ni saltar la incertidumbre de publicación. Lección upstream: tras tool aprobada y Session append ambiguo, `NextStepInterruption` no retenía publicación/guardrails (#4646).
- **Contrato hipotético (tipos propuestos):** `settle_tool_publication(session: &AuthorizedSession, pending: &PendingToolPublication, cancel: &CancelToken) -> Result<PublicationOutcome, PublicationError>`. Entrada: op_id/call_id/approval refs/backend ref/revisión/batch refs; salida `Applied | AlreadyApplied | BlockedUnknown` con revisión. Errores propuestos: `WrongBackend`, `StaleHistory`, `AmbiguousHistory`, `ScopeDenied`, `UnsupportedEvidence`.
- **Fuente de evidencia:** `src/agents/run_state.py:189-231` (O14: `_PendingSessionWrite` retiene session_id, batch, fingerprints, count, response/store y estado acknowledged) · `src/agents/run_internal/session_persistence.py:965-1026,1444-1619` (O13: `save_resumed_turn_items` y `resume_pending_session_write` con verificación de tail exacto — unchanged append, committed no repite, cambiado/ambiguo/partial falla cerrado).
- **Seam VantaDB:** adapter Python/host con `vanta-memory/src/utils/task_checkpoint.rs::TaskCheckpointManager` (NV4), `vanta-memory/src/core/record/l1_writer.rs::persist_planned` y generation log para referencias — no ledger nuevo universal.
- **Acciones:**
  1. Registrar intent + resultado ya realizado → persistir pending en el checkpoint existente → intentar append → comparar frontera exacta autorizada → confirmar antes del siguiente efecto.
  2. Ligar resultado/guardrail/aprobación a la captura del host; envelope mínimo versionado sobre el checkpoint existente.
  3. Fail-closed explícito si el backend no reconcilia; estado ambiguo bloquea aprobación restante.
  4. Versionar envelope; desactivar bloquea continuaciones pendientes conservando datos; reparar por operador/host, no borrar evidencia.
- **Dependencias:** identidad/auth, exclusión real del host y backend; X-OAP-03 si filtra vista, X-OAP-02 si la publicación dispara compaction. Sin dependencia de LLM. Legacy desconocido no adquiere exactly-once.
- **FMEA:** commit-then-raise → retry duplica → reconcile por op/revisión; copia `RunState` en dos workers → doble acción → el host serializa; mismo session_id en otra DB → falso match → backend ref; batch remoto parcial → ambigüedad → fail closed.
- **Criterios de aceptación propuestos:** fallo previo no ejecuta tool; resultado confirmado se publica una vez; timeout postcommit no repite; estado ambiguo bloquea aprobación restante. Observación: códigos/IDs/etapas sin output de la tool.
- **Criterio negativo:** nunca reinvocar la herramienta para reparar publicación ni inferir commit por similitud de texto; si el backend no reconcilia, se declara fail-closed — no se fabrica un commit.
- **Independencia:** una publicación por intento del adapter; útil sin X-OAP-01/02/03 salvo las relaciones señaladas.
- **No objetivos:** no transacción distribuida ni scheduler nuevo; no ejecutar inferencia ni siguiente herramienta sobre publicación incierta. Abierta: garantía de compare del backend.

### X-OAP-05 — Observabilidad acotada sin convertir trazas en recibos

- **Problema:** el diagnóstico de tool/recall puede exfiltrar inputs/outputs y un span exportado puede confundirse con resultado persistido; el estado de observación no es durabilidad.
- **Contrato hipotético (tipos propuestos):** `describe_observation_policy(actor: &Actor, config: &EffectiveConfig) -> Result<ObservationPolicyView, PolicyError>` y `observe_publication(event: &PublicationMetadata, policy: &ObservationPolicyView) -> Result<ObservationStatus, ObservationError>`; salida `Local | Exported | Dropped | Disabled` — nunca `Durable`. Errores propuestos: `DeniedDestination`, `UnsupportedRedaction`.
- **Fuente de evidencia:** `src/agents/run_config.py:53-60,414-443` (O21: `tracing_disabled=false` y default sensible leído de env — describe upstream, no política recomendada) · `src/agents/tracing/processors.py:45-94,698-778` (O22: exporter con endpoint por defecto externo, credenciales de entorno, cola en memoria 8192/batch 128/delay 5s y drop si llena) · `src/agents/tracing/setup.py:16-66` (O23: init lazy + atexit — importar módulo no prueba egreso ni atexit garantiza export durable).
- **Seam VantaDB:** `IntegratedContext`/`CompactionReport` (NV3), generation-log (NV4) y ActivityPanel de Studio existentes; exporter en adapter/host, fuera del motor.
- **Acciones:**
  1. Inventariar campos → clasificar sensibles → resolver configuración efectiva por actor/config → registrar metadata (IDs/timing/códigos) sin payload → exportar solo opt-in con destino/retención aprobados → mostrar drops.
  2. Versionar la política, no migrar trazas antiguas a hechos.
  3. Desactivar exporter no borra historial ni revierte writes; retención externa requiere otro owner.
- **Dependencias:** auth/config y redacción; observa X-OAP-04; independiente de X-OAP-01/X-OAP-02. Retención externa requiere owner separado.
- **FMEA:** trace sensible por default → egreso de datos → vista de destino/política; cola llena → span perdido → drop count, nunca error del write primario; flush timeout → sin evidencia externa → `Unknown` sin repetir la herramienta.
- **Criterios de aceptación propuestos:** flujo normal emite IDs/timing/códigos; input de tool con secreto no aparece por defecto; exporter caído no transforma write aplicado en no aplicado; métricas de dropped/disabled sin texto.
- **Criterio negativo:** un drop de cola o un timeout de flush no transforman un write aplicado en no aplicado; la salida nunca reporta `Durable` — la traza no es un recibo.
- **Independencia:** metadata local primero; independiente de rewind/compaction; solo observa la publicación de X-OAP-04.
- **No objetivos:** no port de threads/scheduler/exporter OpenAI; no certificar privacidad de todos los campos desde un flag. Abierto: contrato de retención/destino del host.
