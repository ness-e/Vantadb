# FIND-742 + FIND-744 — dos tests de WAL que no miden

Ambas filas son la misma clase macro ("un test que no puede fallar / no limpia lo que
crea"), así que se ejecutan en una sola tarea para pagar **un** lock del compilador.
Son **dos defectos distintos** y se commitean por separado:

| Fila | Defecto | Naturaleza |
|---|---|---|
| `FIND-742` | `test_wal_version_mismatch` tiene una aserción **imposible de fallar** (`X == X`) y un fixture que no es lo que su comentario dice | el test **no mide** nada sobre el path que afirma cubrir |
| `FIND-744` | el helper de tests de `wal_sharded.rs` deja un `.shard0.corrupt` (54 B) **suelto en `%TEMP%`** por corrida | el test **mide bien pero no limpia** |

## Contexto

### FIND-742 — la aserción no puede fallar

`src/wal.rs:2587-2619` (numeración previa al cambio). Única aserción de versión:

```rust
assert_eq!(expected_version, WAL_MAX_READABLE_VERSION);
```

`WalHeader::deserialize` construye exactamente ese campo con la misma constante
(`wal.rs:259`, `expected_version: WAL_MAX_READABLE_VERSION`) → la aserción es `X == X`
en **todas** las combinaciones de features: no existe entrada que la ponga roja.

Segundo defecto, independiente: el fixture es
`b"NOT_A_VALID_MAGIC_BYTES_123456"` (30 B). El reader lee 20 B y compara **magic**:
`b"NOT_" != b"VWAL"` → `IncompatibleFormat`. El path de
`Error::WALVersionMismatch` (`wal.rs:286-292`, "version 0 nunca fue un formato válido")
**no lo ejercita ningún test**. El comentario del test afirma que el fixture "uses v0":
falso — el magic corta antes, y la "versión" que se reporta es la de los bytes `A`,`_`
del propio fixture (24385), no 0.

### FIND-744 — el residuo

`src/wal_sharded.rs:999`:

```rust
std::env::temp_dir().join(format!("vanta_test_sharded_{}", rand::random::<u32>()))
```

El nonce evita colisiones, así que el daño no es interferencia: es el **residuo**.
Medido en `%TEMP%` antes del fix (una corrida = un fichero de 54 B):

```
vanta_test_sharded_3122716524.shard0.corrupt | 54 B
vanta_test_sharded_806714666.shard0.corrupt  | 54 B   (tras `nextest -E 'test(sharded)'`)
```

`clean_shards` borra los shard files y el meta, pero **no** los hermanos `<shard>.corrupt`
que crea la cuarentena de `WalWriter::open`. El recolector (`dev-tools/temp-collector.ps1`)
sólo barre **directorios** (`FIND-743`), así que un fichero suelto no lo ve nadie.

**Test que produce el residuo (medido, no inferido):** `test_salvage_truncate_restores_coherent_recovery`
→ delta `+1` por corrida. Sus vecinos `test_salvage_preview_truncated_reports_explicit_discards`
y el resto del filtro `test(sharded)` → delta `0`. Causa: ese test trunca `shard0` a mitad
de record y luego reabre con `ShardedWal::new`, camino que pasa por
`quarantine_corrupt_tail` (`wal.rs:1714`).

## Spec — decisiones (por evidencia, no por ticket)

### FIND-742

| Decisión | Elección | Justificación |
|---|---|---|
| ¿Caso (a) `TempDir` o (b) nombre único para el fixture nuevo? | **(a) `TempDir`** | El test escribe un header v0 y lo abre **dentro** del cuerpo; nadie lee el path después del `Drop`. Mismo criterio que `FIND-735`. |
| ¿Header "a mano" o `WalHeader::new(0)`? | **`WalHeader::new(0)`** | Construye el mismo wire (magic `VWAL` + `format_version = 0` + CRC válido) sin duplicar el layout de 20 B en el test. El "a mano" del ticket pedía control sobre los bytes, no reimplementar `serialize`. |
| ¿`WalHeader::deserialize` o `WalReader::open`? | **`WalReader::open`** | Es el path real que consume el header en disco; `deserialize` solo se cubre por transitividad. Un test con el reader prueba también el read de 20 B. |
| ¿Renombrar el test existente? | **Sí → `test_wal_rejects_foreign_magic`** | El nombre afirmaba lo que el fixture no es (una versión). Dejar el nombre es conservar el mismo defecto que el comentario falso. Sin referencias externas (`rg` sólo lo encuentra en su definición y en docs históricos). |
| ¿Qué sustituye a la aserción tautológica? | `found_magic == b"NOT_"` + `found_version == u16::from_le_bytes([b'A', b'_'])` | Afirma que el reader reporta **los bytes del fixture**, no la constante que él mismo pasa. Ambas pueden fallar. |

### FIND-744

| Decisión | Elección | Justificación |
|---|---|---|
| ¿Caso (a) `TempDir` o (b) nombre único? | **(a) `TempDir`** para los 38 usos | Leído el `mod tests` completo (991-1798): **ningún** test lee su path después del retorno; los `test_reopen_*` reabren dentro del cuerpo. `TempDir` borra el árbol entero, así que `<shard>.corrupt` cae dentro. |
| ¿Cómo se pasa sin tocar 38 cuerpos con lógica nueva? | Helper devuelve `(TempDir, PathBuf)`; call sites pasan a `let (_tmp, path) = test_wal_path();` | El `TempDir` queda como **primer** local → cae último (orden inverso de `Drop`), después de writers/readers. Sin `Deref` mágico ni `thread_local` (el camino aburrido). |
| ¿`close()` explícito? | **Sí, en el test que produce el residuo** (`test_salvage_truncate_restores_coherent_recovery`) | `Drop` traga el error de borrado; `close()` devuelve `io::Result`. Así el no-leak es **falsable** — misma lección que `FIND-735`. |
| ¿Se conserva el nonce en el nombre del fichero? | **Sí** | El `TempDir` ya es único; quitar el nonce sería un cambio sin ganancia (y ruido en el diff). |
