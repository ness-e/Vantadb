## 3. Protocolo de ejecución (cómo corre este plan)

**Orden:** Fase 0 entera antes de Fase 1 (el release manda). Dentro de una fase, por `Wave`; dentro de una wave, en paralelo.

**Fan-out:** `MAX_CONCURRENT = min(3, tareas_en_wave)`, salvo waves marcadas **Rust-heavy** → 2 (contención del lock de `target/`). Cada tarea = un sub-agente con contexto fresco y `pipeline-full.md`.

**Routing:** el campo `Ruta` de cada fila es el `subagent_type`. Nunca un agente genérico si hay especialista.

**Profundidad obligatoria por tarea:** DISCOVERY (task file `docs/dev/tasks/<ID>.md` con blast radius, skills SDP, steps atómicos) → EJECUCIÓN (≤100 líneas por step, verify por step) → CIERRE (verify full scoped + OCR `dev-tools/ocr-review.ps1` + review P2-01 por agente DISTINTO + commit local + `progreso`).

**Gates activos:** **D** (blast radius >10 archivos · hot path · API pública · contrato ambiguo) pregunta antes de codificar; **V** (2 fallos con el mismo error) pregunta; **C** (colaterales al cerrar) auto + ticket `FIND-*`.

**Recuperación:** resultado no-DONE → escalera SARL (`subagent-recovery.md`): RESUME misma sesión → RETRY fresco → STRATEGY → ESCALATE. Nunca `FAILED` sin pasar por SARL.

**Verificación:** doble — el sub-agente corre su contrato, el orquestador lo **re-corre** antes de dar la tarea por cerrada (`campaign_verify_cmd`; si el MCP falla por el bug de plan ambiguo, se corre el comando en shell y se anota).

**Monitor de CI:** sub-agente `vanta-lead` en modo lectura (`gh run view/list`), solo cuando una tarea lo declara en su contrato (F0.1, F0.5, `FIND-328`, `FIND-317`).

**Commits:** uno por tarea, `tipo(scope): resumen (ID)`, autoría del owner, sin trailers de agente. `git add` solo de las rutas de la tarea (el árbol puede tener trabajo de otra sesión).

**Concurrencia con otras sesiones:** antes de cada wave, `git status` debe estar limpio o solo con cambios propios. Si hay WIP ajeno → no arrancar esa wave (probe 4d).

Reglas de este orden:
- **Ejecución continua sin cupo artificial** (decisión del owner, 2026-11-24): se corren F1, F2 y luego F3 **por valor**, sin parar, hasta que la ventana cierre el 1-dic. No se descarta ninguna fila por "no cabe": si no se termina, sale en `v0.10.x`.
- Cada wave cierra con `git push origin develop` + CI verde **antes** de arrancar la siguiente. Un rojo no se arrastra.
- Una fila que en DISCOVERY resulte ser ≥3d se mueve a Fase 3 con justificación en su task file (no bloquea el release por sí sola).
- Una fila que en DISCOVERY resulte **stale** (ya implementada) se cierra con evidencia (SKIP) en vez de ejecutarse.
- El release (bloque D) se dispara al **cerrar la ventana**, no al agotar la lista: exige que toda fila ejecutada tenga su `progreso` aplicado (fila fuera del Backlog + entrada en `docs/dev/avance/`) y que `develop` esté verde.
- Fase 3 no es requisito del release: lo que se cierre antes suma; lo que no, sale en `v0.10.x`/`v0.11.0` con su fila viva.

## 3.c Protocolo de paralelización por carriles (2026-11-24)

> Objetivo: máximo throughput sin solapes. Lo que limita no es el número de agentes sino **`target/`,
> el índice de git y los ficheros compartidos**. Cada tarea declara su carril; un carril tiene cupo.

| Carril | Cupo | Quién | Regla de oro |
|---|---|---|---|
| **R — Rust** | 2 | `vanta-worker`, `vanta-engine`, `vanta-tuner`, `vanta-chaos` | todo build/test comparte `target/`: más de 2 no acelera, solo encola. `cargo ... -j 2` |
| **D — Docs** | 4 | `vanta-docs` | sin `cargo`; cada agente edita ficheros de su lista y nada más |
| **C — CI / scripts** | 3 | `vanta-lead` | workflows, `dev-tools/*.ps1`, triage con `gh` (lectura); sin builds pesados |
| **A — Arquitectura / spec** | 2 | `vanta-arch`, `vanta-research` | read-only o specs: pueden correr en paralelo con todo |

**Batch, no tarea a tarea.** Una wave se cierra así, una sola vez:
1. los agentes dejan sus cambios y commitean **solo sus rutas** (si `index.lock` existe: esperar 5 s y reintentar, hasta 6 veces);
2. el orquestador corre **una** verificación de batch: `pwsh dev-tools/verify_changed.ps1` (rápido) y, si tocó Rust, `pwsh dev-tools/verify.ps1`;
3. **un** `git push origin develop`;
4. **un** monitor de CI sobre ese SHA (`vanta-lead`, read-only) antes de abrir la wave siguiente.

Exceptiones a "verificar al final": el agente **sí** corre su test acotado (`cargo nextest -p <crate> -E 'test(<x>)'`, `node --test`, `pwsh` del script) porque es barato, y detecta el error cuando el contexto aún está fresco. Lo que **no** se corre por tarea es la suite completa, `clippy` global, `fmt --check`, `deny` ni el push: eso es de batch.

## 10.b Secuencia real del release (medida en los workflows, no asumida)

```
1. merge develop → main                        (owner OK)  → dispara release.yml (push a main)
2. release-plz pr                              → actualiza su PR a la versión computada (0.10.0)
3. checks del PR + merge del PR release-plz-*  (owner OK)  → release-plz release publica crates + crea el Release/tag
4. release: published                          → release-binaries.yml construye los 5 targets solo
5. assets listos                               → Formula/vantadb.rb = 0.10.0 + los 4 sha256 (un commit)
6. verify-release.ps1 -Tag v0.10.0 -Smoke      → smoke real de registries + assets
7. sync develop ← main (ff-only)                → evita que un develop→main futuro revierta fixes
```

Consecuencias sobre el plan original:
- El **manifest no se toca a mano** (lo escribe release.yml en el paso 3); el gate de igualdad de versión lo exige.
- El **dispatch manual de binarios no es el camino normal**: los construye el evento `release: published`. `workflow_dispatch` queda para backfill.
- La **fórmula se actualiza después** de que existan los assets: `version` y `sha256` son atómicos, y durante la ventana `brew install` sigue sirviendo `0.9.0` (riesgo ya registrado).
- El único paso que un agente puede hacer sin decisión del owner es el 5 (fórmula) y el 6 (verificación); 1, 3 y 7 son del owner.
